# Software Development

**核心约束**：改动范围以完成需求并通过验收为上限。
不得伪造测试结果，不得把未验证的代码描述为已完成。

> 本文件自包含：执行所需的红线已内联。完整规范可在项目根目录的
> `.ai-standards/core/` 与 `.ai-standards/standards/` 下按需查阅，
> 但**不依赖**这些文件即可完成本 Skill。
> **渐进加载**：通用工程红线读 `core/` 对应文件；具体语言/框架写法读 `standards/`
> 对应规范，仅在任务需要时读取。**不假设能访问其它会话的上下文**，
> 以当前工作区实际文件、现有代码与本轮验收标准为准。禁止写 `../../core/xxx.md` 这类链接。

## 前置约束（内联红线）

- 修改代码之前必须先理解现有项目；不得凭空假设文件、接口、数据库字段或依赖。
- 未经明确授权不得大规模重构、更换技术栈、新增第三方依赖、删除既有功能、
  修改公共 API 契约、覆盖用户已有文件。
- 数据库结构变更必须同时具备迁移、回滚、旧数据兼容、回填/双写、影响评估与验证方式。
- 每个文件出现在改动集里都必须能回答「为什么」。不混合行为变更与无关格式化。
- 验证结果必须来自**实际运行**的命令；区分「已验证通过 / 已运行但失败 /
  未运行（原因）」。无法运行时给出需人工验证清单。
- 完成后必须汇报：修改内容、验证结果、风险与未决项、后续动作。

## 触发场景

- 需求与验收标准已明确，开始实现；
- 修复已定位的缺陷，并需要补回归测试；
- 为既有功能补测试或小范围改进；
- 用户说「按这个需求实现」「把这个 bug 修了」「改一下这几个文件」。

## 何时不使用

- 需求模糊、验收标准缺失（先用 `requirements-analysis`）；
- 需要架构选型或模块划分（先用 `architecture-design`）；
- 只需只读分析现状（用 `project-analysis`）或审查既有改动（用 `code-review`）；
- 涉及高风险/不可逆操作且尚未取得授权——先澄清，不进入实施。

**判断依据**：若「做什么、做到什么算完成」已明确，用本 Skill 落地；
若上游尚未定义清楚，先补齐上游而非猜测着写代码。

## 适用范围

- 输入：需求与验收标准、实施边界、项目规范与运行命令。
- 权限边界：允许修改实施边界内的源码与测试；边界外文件不改。
- 语言/框架无关；具体写法按项目内 `.ai-standards/standards/` 下对应规范执行（若存在）。

## 与其它 Skill 配合

| 关系 | 说明 |
| --- | --- |
| 上游输入 | 验收标准来自 `requirements-analysis`；实施边界与决策可来自 `architecture-design` |
| 下游消费 | 改动集与验证结果交给 `code-review` 做独立审查 |
| 运行时依赖 | **无**。本 Skill 可独立调用（如明确的 Bug 修复无需先跑分析/设计） |
| 典型组合 | 复杂任务按「分析 → 需求 → 设计 → 实施 → 审查」组合；小改动可直接进入本 Skill |

> 组合是**可选**的典型流程，不是强制顺序；简单 Bug 修复可直接用本 Skill，
> 不必先执行前面的 Skill。审查与实施分离，本 Skill 不自我审查下结论。

## 执行步骤

1. **阅读项目规范**：读取项目入口文档、规范文件与既有约定；
   确认 lint / 类型检查 / 测试 / 构建的实际命令。
2. **理解需求和验收标准**：把每条验收标准映射为可观察行为；
   缺一条就回到 `requirements-analysis`，不自行补写。
3. **检查现有实现**：定位相关模块与调用方，查找可复用能力；
   读实现确认行为、错误语义与边界条件，不凭函数名猜测。
4. **制定最小修改计划**：列出文件清单 + 每文件改动说明 + 原因；
   明确「不改什么」；涉及高风险操作时先取得授权。
5. **实施编码**：按最小计划逐文件修改；遵守语言规范与
   [编码自检清单](references/coding-checklist.md)。
6. **编写或更新测试**：覆盖正常、边界、异常、回归四类；
   缺陷修复必须先有一个在修复前失败的用例；权限相关改动补越权用例。
7. **执行质量检查**：实际运行静态检查、类型检查、测试、构建；
   记录命令与真实输出，不用「应该会通过」代替运行。
   composite 项目引用结构需显式指定子配置，否则可能是零检查的假阴性。
8. **修复发现的问题**：定位根因后修复，重跑受影响的检查；
   不改断言绕过失败、不删除失败用例、不跳过检查。
9. **检查回归风险**：复查 `git diff`，确认无无关文件、无调试代码、无密钥、
   无未授权依赖、无公共契约变更；列出可能受影响的既有功能。
10. **输出实施报告**：按 [实施报告模板](assets/implementation-report-template.md) 填写，
    四项内容缺一不可。

## 输入要求

| 输入 | 必需 | 缺失时 |
| --- | --- | --- |
| 需求与验收标准 | 是 | 退回 `requirements-analysis`，不自行编造 |
| 实施边界（允许/禁止改动） | 是 | 向用户澄清，不扩大范围 |
| 项目运行命令 | 是 | 从项目文档/配置确认；确认不到则把相关检查列为「未运行项」 |
| 设计决策记录 | 否 | 标为缺失，遇到取舍时发起澄清 |

## 输出要求

- 代码与测试改动（文件列表 + 每文件改动说明）；
- 实施报告（模板见 [assets/implementation-report-template.md](assets/implementation-report-template.md)），
  包含：修改内容、验证结果、风险与未决项、后续动作；
- 验证结果三段式列出：`已验证通过` / `已运行但失败` / `未运行（原因）`，
  附实际命令与输出摘要；
- 未运行项给出**需人工验证清单**（命令 + 预期结果 + 风险）；
- 任何失败或未运行项必须在报告**开头**显著说明。

## 质量检查

- [ ] 每个改动文件都能追溯到需求或验收标准；
- [ ] 没有与需求无关的格式化/重命名/依赖升级 diff；
- [ ] 公开接口变更已获授权，旧调用方仍可用（或已提供迁移）；
- [ ] 正常、边界、异常、回归四类测试齐备，且缺陷修复有「先失败」的用例；
- [ ] 输入校验在边界完成，错误路径未被吞掉，日志不含敏感数据；
- [ ] 静态检查、类型检查、测试、构建均**实际运行**并记录结果；
- [ ] 类型检查指定了正确的配置；构建与类型检查分别验证；
- [ ] `git diff` 已复查，无调试代码、临时开关、硬编码环境值或密钥；
- [ ] 报告如实区分三种状态，没有夸大完成度。

## 完成标准

- 10 个步骤全部执行；
- 每条验收标准都有实现与对应测试（或明确标注未覆盖原因）；
- 质量检查全部实际运行，结果可追溯；失败与未运行项已显著说明；
- 回归风险已列出，后续动作（迁移/配置/重启/文档）已写明；
- 未引入未授权依赖、未改变公共契约、未删除既有功能。

## 异常情况处理

| 情况 | 处理 |
| --- | --- |
| 验收标准缺失或矛盾 | 停止实施，回到 `requirements-analysis` 并发起澄清 |
| 现有实现与需求冲突 | 写出冲突证据，请求澄清，不擅自改写既有行为 |
| 缺少运行命令 / 环境受限 | 列出无法运行的检查与原因，给出人工验证清单，不表述为「已通过」 |
| 测试失败 | 定位根因修复并重跑；不改断言绕过、不删用例；失败如实汇报 |
| 发现需要大规模重构才能完成 | 停止并说明范围与理由，等待明确授权，不擅自扩大改动 |
| 涉及数据库结构变更 | 缺迁移/回滚/兼容方案则不实施，先补齐并获授权 |
| 构建通过但类型检查未跑 | 明确标注类型检查「未运行」，不把构建成功当作类型安全 |
