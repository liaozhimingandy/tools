# Architecture Design

**核心约束**：先分析现有架构，再谈方案。不为了使用设计模式而引入不必要的抽象；
不擅自更换技术栈、新增依赖或修改公共契约。

> 本文件自包含：执行所需的红线与评估维度已内联或打包在本技能目录内。完整规范可在
> 项目根目录的 `.ai-standards/core/`（`architecture-principles.md`、`security-principles.md`）
> 与 `.ai-standards/standards/` 下按需查阅，但**不依赖**这些文件即可完成本 Skill。
> **渐进加载**：仅当任务确需通用原则的细节时才读取上述文件；**不假设能访问其它会话的
> 上下文**，一切以当前工作区实际代码与用户本轮输入为准。
> 禁止写 `../../core/xxx.md` 这类安装后会失效的链接。

## 前置约束（内联红线）

- 现状描述必须基于代码事实；无法确认的部分标为「待确认」，不用推测填补。
- 未经明确授权不得大规模重构、更换技术栈/框架、新增第三方依赖、
  删除既有功能、修改公共 API 契约。
- 数据库结构变更必须同时给出迁移、回滚、旧数据兼容、回填/双写策略、
  影响评估与验证方式；缺任一项不得实施。
- 依赖方向保持单向无环；每份可写数据有唯一所有者。
- 方案比较必须给出结论，不得以「各有优劣」结束。

## 触发场景

- 新增一个子系统/模块，需要确定边界与落点；
- 现有架构出现重复职责、循环依赖或数据归属不清；
- 需要在多个技术方案之间做选择；
- 用户说「设计一下架构」「给个技术方案」「这个模块放哪里」「记录设计决策」。

## 何时不使用

- 需求尚未明确、验收标准缺失（先用 `requirements-analysis`）；
- 只需最小代码改动且边界不变（用 `software-development`）；
- 需要对既有改动给出审查结论（用 `code-review`）；
- 只需了解项目现状、还不到设计阶段（用 `project-analysis`）。

**判断依据**：若问题涉及「模块怎么划、方案怎么选、边界怎么定」，用本 Skill；
若「怎么划」已有定论、只差落地或验证，用下游 Skill。

## 适用范围

- 输入：需求与验收标准、项目现状（可来自 `project-analysis`）、约束条件。
- 权限边界：只读调研 + 产出设计文档；不实施编码，不写入项目代码。
- 允许产出明确标注的验证性原型，但原型不进入交付且不落在项目源码目录。

## 与其它 Skill 配合

| 关系 | 说明 |
| --- | --- |
| 上游输入 | 需求与验收标准来自 `requirements-analysis`；现状事实可来自 `project-analysis` |
| 下游消费 | 设计文档 + 决策记录 + 实施边界交给 `software-development` 落地 |
| 运行时依赖 | **无**。本 Skill 可独立调用；若输入缺失则退回澄清，而非自动调用其它 Skill |
| 典型组合 | 复杂任务按「分析 → 需求 → 设计 → 实施 → 审查」组合；需求与技术栈已定时可跳过本 Skill |

> 组合是**可选**的典型流程，不是强制顺序；不得因为「没有前置文档」就虚构需求或现状。

## 执行步骤

1. **先分析现有架构**：列出模块清单与职责、依赖方向、数据归属、关键调用链、
   外部系统、部署形态、已有的约束与妥协；每项附来源路径。
2. **确认架构问题**：把需求翻译成"现有架构哪里不足以支撑"，区分
   「必须解决」与「顺带可改善」；后者不进入本次范围。
3. **识别模块职责**：为每个相关模块写一句话职责陈述，明确公开接口、
   不变量与数据所有者；标出需要新增/拆分的边界。
4. **评估技术方案**：至少比较「最小改动方案」与一个替代方案，
   按 [方案评估维度](references/evaluation-dimensions.md) 逐项填写并给出结论。
5. **评估依赖关系**：列出新增/变更的依赖方向与第三方依赖；
   确认无环、无隐藏耦合；新增依赖必须标注「需用户授权」。
6. **分析扩展性和维护成本**：说明扩展点是否对应真实需求、谁能扩展、
   维护者需要多少背景知识；删除只有一个实现的接口或只有一层转发的包装。
7. **考虑安全性和性能**：明确每个信任边界的认证/授权/输入校验，
   多租户隔离的服务端强制点；给出分页/批量上限/超时/并发/缓存一致性假设。
8. **明确数据流**：对关键用例追踪入口 → 校验 → 转换 → 唯一写入点 → 响应，
   标注事务边界、异步分界与失败时的数据状态。
9. **输出架构设计文档**：按 [设计文档模板](assets/design-template.md) 组织，
   包含实施边界（允许改/禁止改的模块）与验收映射。
10. **记录重要设计决策**：按 [决策记录模板](assets/decision-template.md)，
    每条写「问题 → 备选 → 选择 → 理由 → 后果 → 重新评估条件」。
    必要时用 Mermaid 绘制架构图与流程图。

## 输入要求

| 输入 | 必需 | 缺失时 |
| --- | --- | --- |
| 需求文档与验收标准 | 是 | 退回 `requirements-analysis`，不自行补写需求 |
| 项目结构与技术栈事实 | 是 | 执行只读现状调研，不靠猜测 |
| 约束（性能/合规/兼容/时间） | 否 | 标为假设并列入待确认清单 |
| 现有架构文档 / 既有决策记录 | 否 | 明确写「未找到」，不假定其存在 |

## 输出要求

Markdown 架构设计文档，含以下 8 部分（模板见
[assets/design-template.md](assets/design-template.md)）：

1. 现状与约束（基于代码事实，标出待确认项）；
2. 问题定义与验收标准；
3. 模块职责与边界（依赖方向、数据归属）；
4. 方案比较表与有理由的结论；
5. 关键用例的数据流；
6. 安全与性能考量；
7. 迁移 / 回滚 / 兼容方案；
8. 实施边界与验收映射。

外加独立的设计决策记录（[模板](assets/decision-template.md)）与待确认事项清单。

## 质量检查

- [ ] 现状描述可被代码验证，无凭空假设的文件/接口/字段；
- [ ] 每个模块有唯一职责陈述，每份可写数据有唯一所有者；
- [ ] 依赖图单向无环，新增依赖都被标注为需授权；
- [ ] 方案比较覆盖需求、改动范围、依赖、维护、安全、性能、回滚、成本 8 个维度；
- [ ] 明确写出了结论与理由，不是「各有优劣」；
- [ ] 安全章节写明对象级授权与多租户隔离的强制点；
- [ ] 数据流标注唯一写入点与失败时的数据状态；
- [ ] 数据库相关设计包含迁移、回滚与旧数据兼容；
- [ ] 没有为使用设计模式而引入的抽象层；
- [ ] 设计决策可被后续接手者独立理解。

## 完成标准

- 10 个步骤全部执行，文档 8 部分 + 决策记录齐全；
- 所有待确认事项已单列，高风险项已发起澄清（背景 + 选项 + 后果）；
- 实施边界明确到模块，可直接作为 `software-development` 的输入；
- 项目代码零改动，未实施未经授权的变更。

## 异常情况处理

| 情况 | 处理 |
| --- | --- |
| 现状与需求描述冲突 | 写出冲突证据，作为阻塞项请求澄清，不按需求描述强行设计 |
| 项目过小 / 无清晰模块 | 如实说明"当前无明显边界"，给出最小模块划分，不硬套分层架构 |
| 缺少性能/容量数据 | 标为假设，写明「什么条件下需重新评估」，不编造数字 |
| 方案都需要新增依赖 | 全部列为需授权，并补充一个不新增依赖的最小方案 |
| 涉及破坏性契约变更 | 单列为阻塞项，给出兼容路径与迁移步骤，等待授权 |
| 用户要求「顺便把代码写了」 | 拒绝在本 Skill 内实施，提示改用 `software-development` |
