# 测试原则

> **规范用语**：定义见 [README.md](README.md) §2；**冲突处理规则**以
> [README.md](README.md) §4 为唯一权威。
> **前提**：[engineering-principles.md](engineering-principles.md)（最小必要修改、异常处理），
> [ai-behavior.md](ai-behavior.md) §4（不得伪造测试结果、不得把未验证代码说成已完成）。
> **红线**：测试结论 MUST 来自**实际执行**的命令输出；**MUST NOT** 凭推测填写「通过」。

---

## 文档目的

定义测试的目标、层次、编写原则、执行流程与质量报告要求，
使 AI 在修改代码后能选择与改动范围相匹配的验证手段，并如实报告真实结果。
本文件回答「怎么证明改动是对的」，不回答「系统怎么分层」。

---

## 适用范围

适用于所有需要验证行为正确性的改动：新增功能、缺陷修复、重构、
配置与依赖变更、安全逻辑变更、以及提交前的验收。
不适用于具体测试框架的用法（见 [../standards/](../standards/) 与项目自身配置）。

---

## 核心规范

### 1. 测试目标与测试层次

**测试目标**：验证功能正确性、防止已有功能回归、验证边界条件、
验证异常路径、验证重要业务规则。测试不是为了让报告里出现「全部通过」。

- **MUST** 在能捕获该缺陷的最低层写测试；越往上越慢、越脆弱、越贵。

| 层 | 验证什么 | 允许依赖 | 典型数量 |
| --- | --- | --- | --- |
| 单元测试 | 单个函数/组件的纯逻辑与分支 | 无外部 I/O | 多 |
| 集成测试 | 模块间协作、数据库/文件系统/消息队列真实交互 | 真实或受控的本地依赖 | 中 |
| API 测试 | HTTP 契约、状态码、错误结构、认证与对象级授权 | 运行中的应用 + 测试数据库 | 中 |
| 端到端测试 | 关键业务链路在接近生产环境下的完整行为 | 完整环境 | 少 |
| 回归测试 | 已修复缺陷不再复现 | 同缺陷所在层 | 按需 |
| 性能测试 | 容量、延迟、资源消耗是否满足假设 | 受控的基准环境 | 按需 |
| 安全测试 | 未认证/越权/跨租户/注入等路径是否被拒绝 | 同 API 或集成层 | 按需 |

- **SHOULD NOT** 要求所有项目都采用全部测试类型；
  **SHOULD** 根据项目规模、风险与改动范围选择，并在报告中说明选择理由。
- **MUST NOT** 让同一行为在每一层重复测试；上层只验证下层无法验证的「接线是否正确」。
- **SHOULD NOT** 把能用单元/集成覆盖的逻辑写成端到端测试。
- 判断依据：这条测试能否在更低层捕获同一缺陷？若能，为什么没放在低层？

### 2. 单元测试

- **MUST** 让测试一个明确行为，快速、确定、可重复、无隐藏顺序依赖。
- **SHOULD** 让一个测试断言一个行为，测试名写清「条件 → 行为」，
  **MUST NOT** 使用 `test1`、`test_ok` 之类的名字。
- **SHOULD** 遵循 Arrange–Act–Assert；**SHOULD NOT** 把大量断言堆在一个用例里。
- **MUST NOT** 依赖真实时钟、随机数、网络、当前工作目录或执行顺序；
  依赖 MUST 通过注入控制。
- **MUST** 让测试失败信息能直接指出哪个条件、哪个期望值不满足。
- 判断依据：随机打乱执行顺序，测试是否仍通过？

### 3. 集成测试

- **MUST** 验证真实协作，重点在边界、事务、配置与外部系统交互。
- **SHOULD** 使用真实的本地依赖（数据库、缓存、临时文件系统）而非全面 Mock，
  否则「集成」失去意义。
- **MUST** 让每个用例自行准备并清理数据，**MUST NOT** 让测试间共享可变状态。
- **SHOULD** 覆盖连接失败、超时、部分写入、事务回滚等真实故障模式。
- 判断依据：测试是否在没有网络/没有预置数据库的前提下可重复运行？

### 4. API 测试

- **MUST** 把接口当作契约来测，而不仅是「能返回 200」。

每个接口至少覆盖：

1. 正常请求：状态码、响应字段结构、字段类型；
2. 输入校验：缺字段、类型错、超长、越界、非法枚举、空集合；
3. 认证：未登录、过期/无效令牌、越权身份；
4. **对象级授权**：换一个资源 ID MUST 被拒绝，见
   [security-principles.md](security-principles.md) §13；
5. 错误语义：稳定的错误码与结构，不泄漏堆栈或内部路径；
6. 幂等性与并发（针对写接口）；
7. 分页、排序、过滤的边界行为。

契约细节见 [../standards/backend/api.md](../standards/backend/api.md)。
判断依据：把资源 ID 换成他人 ID 的用例是否存在且确实失败？

### 5. 端到端测试

- **SHOULD** 只覆盖少数最关键业务链路，且 MUST 保持稳定。
- 选择标准：影响收入/数据一致性/安全、跨多个系统、故障代价高的链路。
- **MUST** 用显式等待代替固定 `sleep`；
  **SHOULD NOT** 依赖 DOM 结构中的偶然属性做定位。
- **SHOULD** 在失败时保留可诊断信息（截图、日志、请求 ID），
  但 **MUST NOT** 包含敏感数据。
- **MUST NOT** 靠无限重试掩盖不稳定；**SHOULD** 先修复根因。
- 判断依据：这条链路是否能在更低层被覆盖？若不能，说明为什么。

### 6. 边界测试

- **MUST** 对每个输入维度测试边界值与边界外值。
- 数值：0、1、最大值、最大值 +1、负数、精度极限。
- 字符串：空串、仅空白、最小/最大长度、Unicode、特殊字符、超长。
- 集合：空、单元素、批量上限、超过上限、含重复项。
- 时间：时区切换、月末/闰日、夏令时、超时临界点、过期恰好等于当前时刻。
- 状态：初始态、终态、非法状态转换、重复操作（幂等）。
- 判断依据：新增参数是否列出了边界值并至少测了两侧？

### 7. 异常测试

- **MUST** 让失败路径和成功路径一样被测到。
- 覆盖：依赖不可用、超时、返回异常数据、权限不足、资源不存在、
  并发冲突、事务回滚、部分成功。
- **MUST** 断言「如何失败」：错误类型/错误码、是否有副作用、
  数据是否保持一致、是否留下可观察信号（日志、指标、告警）。
- **SHOULD** 验证重试与降级策略确实按设计生效，且不会无限重试。
- **MUST NOT** 用「捕获所有异常然后断言不抛错」来伪造成功。
- 判断依据：外部依赖抛错时，系统是否仍处于可恢复状态？

### 8. 回归测试

- **MUST** 为每个修复的缺陷留下一个能复现该缺陷的测试。
- 流程：先写一个在当前代码上**失败**的测试 → 修复 → 确认该测试通过 →
  确认原有测试仍通过。
- **SHOULD** 把回归测试放在能捕获该缺陷的最低层，并命名或注释关联缺陷标识。
- **MUST NOT** 删除失败测试来「变绿」；修改公开行为时 MUST 检查并更新受影响的既有断言。
- **SHOULD** 在发布前运行完整测试套件，而非只跑本次改动相关的用例。
- 判断依据：这次修复是否新增了测试？该测试在修复前是否确实失败？

### 9. 测试数据管理

- **MUST** 让测试数据可重建、可隔离、不含真实生产数据。
- **MUST** 在测试内构造数据或使用受版本控制的 fixture，
  **MUST NOT** 依赖开发者本机状态。
- **MUST** 让每个用例自行 setup/teardown；并行执行时 MUST NOT 互相污染。
- **MUST NOT** 把含个人信息的样本提交到仓库；生产数据 MUST 脱敏后才能用于测试。
- **SHOULD** 在需要固定时间/随机数/ID 时注入确定值，
  **MUST NOT** 使用「碰巧唯一」的时间戳。
- 判断依据：清空数据库后从零运行测试，结果是否一致？仓库中是否有真实用户数据？

### 10. Mock 使用边界

- **MUST** 让 Mock 用来隔离**不可控因素**，**MUST NOT** 用来绕过真实行为验证。

| 适合 Mock | 不适合 Mock |
| --- | --- |
| 时钟、随机数、UUID | 被测模块自身的业务逻辑 |
| 第三方网络服务（无测试环境时） | 数据库访问（应有集成测试覆盖真实行为） |
| 发送邮件/短信/支付的外部副作用 | 认证与授权判定 |
| 尚未实现、但契约已约定的接口 | 复杂到需要 Mock 才测得动的代码（说明设计有问题） |

- **MUST** 让 Mock 返回值贴近真实契约（含错误形态），
  **MUST NOT** 只返回「永远成功」。
- **SHOULD** 让被 Mock 的行为至少有一个集成/API 层测试覆盖真实实现。
- **SHOULD NOT** 过度断言内部调用；那会让重构寸步难行。
- 判断依据：如果去掉这个 Mock，测试是否还能跑？删掉它是否更可信？

### 11. 覆盖率与质量的区别

- **MUST** 明确区分覆盖率是「执行到了哪些代码」，不是「验证对了哪些行为」。
- **MUST NOT** 把覆盖率数字当作质量结论；高覆盖率可以由只调用不断言的测试制造。
- **SHOULD** 优先关注关键分支、错误路径、边界条件、权限判定、
  数据一致性是否被**断言**。
- **SHOULD NOT** 用覆盖率做排名或设硬性门槛；
  它适合用来找「完全没被触碰的模块」。
- **SHOULD** 用「故意引入缺陷看测试是否失败」检验测试有效性。
- **MUST** 在报告中区分「覆盖率数字」与「哪些行为已被验证」。
- 判断依据：新增的分支是否有对应断言？失败的测试是否真的会失败？

### 12. 测试执行与汇报

修改代码后 **MUST** 按顺序完成：

1. **检查项目已有测试方式**：读取项目配置与既有测试命令，不凭记忆猜；
2. **选择与修改范围相匹配的测试**：按 §1 分层选择，不盲目跑全量也不只跑一行；
3. **执行相关测试**：实际运行并记录命令；
4. **执行必要的静态检查**（lint / 类型检查 / 格式化 / 构建）；
5. **检查测试结果**：对失败逐一分析原因，不让失败悬空；
6. **明确报告未执行的测试及原因**：给出需人工验证的清单（命令、预期结果、风险）。

- **MUST NOT** 虚构测试结果、**MUST NOT** 将未执行的测试描述为通过、
  **MUST NOT** 隐瞒测试失败、**MUST NOT** 将部分测试通过描述为全部通过。
- **MUST NOT** 为了让测试通过而删除有效断言、降低测试标准或修改测试使其绕过失败。
- **MUST NOT** 把 lint / 类型检查 / 构建结果当作测试结果，见
  [ai-behavior.md](ai-behavior.md) §4。
- **MAY** 用项目自带的聚合脚本一次运行多个层次，但 **MUST** 分别记录各层的命令与结果。
- **MUST** 明确区分三种状态：`已验证通过` / `已运行但失败` / `未运行（原因）`；
  环境不具备时 MUST 如实标注，见 [ai-behavior.md](ai-behavior.md) §4、§6。
- **SHOULD** 在实施报告中分别列出：通过项、失败项、未执行项、已知风险。
- 判断依据：报告中每个「通过」是否都能对应一条真实命令输出？

## 禁止事项

索引式汇总（规则正文见对应章节，此处不重复定义）：

- **MUST NOT** 凭推测填写「通过」、编造命令输出、把 lint/类型检查/构建当作测试（§12）。
- **MUST NOT** 将未执行的测试描述为通过、隐瞒失败、把部分通过说成全部通过（§12）。
- **MUST NOT** 删除有效断言、删除失败用例、修改测试绕过失败、跳过检查让套件变绿（§8、§12）。
- **MUST NOT** 让测试依赖真实时钟/网络/执行顺序，或在测试间共享可变状态（§2、§3）。
- **MUST NOT** 把含个人信息或真实生产数据的样本提交到仓库（§9）。
- **MUST NOT** 用「捕获所有异常然后断言不抛错」伪造成功（§7）。
- **MUST NOT** 用 Mock 替代认证/授权判定或被测模块自身的业务逻辑（§10）。
- **MUST NOT** 把覆盖率数字当作质量结论（§11）。

## 验收要求

- [ ] 新增/修改的行为有对应测试，且测试放在能捕获缺陷的最低层（§1）。
- [ ] 边界值两侧、异常路径、越权身份均有断言（§4、§6、§7）。
- [ ] 缺陷修复新增的回归测试在修复前确实失败（§8）。
- [ ] 测试可重复执行：随机打乱顺序、清空数据库后结果一致（§2、§9）。
- [ ] 被 Mock 的行为至少有一处集成/API 层真实覆盖（§10）。
- [ ] §12 的 6 个执行步骤已按顺序完成，命令与真实输出可追溯。
- [ ] 报告分别列出通过项 / 失败项 / 未执行项（含原因）/ 已知风险，数字来自实际输出。
- [ ] 未运行的项目已给出需人工验证的清单（命令、预期结果、风险）。
- [ ] 违反任何 `SHOULD` / `SHOULD NOT` 时已写明理由（[README.md](README.md) §2）。
