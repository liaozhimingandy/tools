# 安全原则

> **规范用语**：定义见 [README.md](README.md) §2；**冲突处理规则**以
> [README.md](README.md) §4 为唯一权威（其中明确规定：安全要求
> **MUST NOT** 因普通项目约定而被忽略）。
> **前提**：[ai-behavior.md](ai-behavior.md) 禁止 AI 擅自扩大权限面或修改安全契约。

安全是默认约束，不是上线前的检查项。每节末尾的「判断依据」供
`code-review` Skill 与人工评审逐条核对。

---

## 文档目的

定义与框架无关的通用安全红线，使 AI 在处理输入输出、身份、权限、数据持久化、
外部依赖与敏感逻辑变更时，有明确、可核对的禁止事项与验证方法。

---

## 适用范围

适用于所有涉及外部输入、身份与权限、敏感数据、数据持久化、文件上传、
出站请求、第三方依赖、以及认证/授权/密钥/支付/用户数据相关逻辑的改动。
不适用于具体框架的安全 API 用法（见
[../standards/backend/](../standards/backend/) 与
[../standards/frontend/](../standards/frontend/)）。

---

## 核心规范

### 1. 身份认证与授权分离

- **MUST** 让认证（你是谁）与授权（你能对哪个对象做什么）独立实现、独立测试。
- **MUST NOT** 把「登录了吗」与「是不是这个资源的所有者/成员」合并成一个布尔值；
  认证通过不代表授权通过，每个敏感操作都要重新判定权限。
- **MUST** 让授权决策基于服务端会话/令牌中的可信身份，
  **MUST NOT** 默认信任请求体里的用户 ID 或客户端传来的身份信息。
- **SHOULD** 为角色变更、权限回收提供已签发凭据的失效路径。
- 判断依据：把用户 A 的 ID 换成用户 B 的 ID，接口是否仍返回 B 的数据？

### 2. 最小权限原则

- **MUST** 让每个主体只获得完成当前操作所必需的最小权限与最短有效期。
- **MUST** 采用默认拒绝（deny by default）：未显式允许的操作一律拒绝。
- **SHOULD** 按读写需求分离数据库账号；应用默认账号 **MUST NOT** 具备 DDL / 管理员权限。
- **SHOULD** 让服务间调用使用限定范围的服务凭据，
  **MUST NOT** 复用超级管理员凭据。
- **MUST** 让临时提权有范围、有期限、有审计；**MUST NOT** 把调试用高权限留在配置里。
- 判断依据：新增的服务账号/角色是否只被授予它实际用到的权限？

### 3. SQL 注入与不安全反序列化

- **MUST** 让任何 SQL 中的值走参数绑定；**MUST NOT** 用字符串拼接构造
  `WHERE`、值、`IN` 列表；标识符 MUST NOT 来自未经白名单校验的输入。
- **MUST** 使用参数化查询 / 预编译语句；表名、列名、排序方向等无法参数化的部分，
  MUST 映射到服务端白名单枚举。
- **MUST** 让 ORM 的原生 SQL 入口、`.raw()`、字符串插值同样受本规则约束；
  动态查询构造器 MUST 保证用户输入只能成为「值」，不能成为「语法」。
- **MUST NOT** 对来自不可信来源的数据做不安全反序列化
  （按类型白名单校验，不启用任意类型还原）。
- 判断依据：搜索仓库中是否存在把请求参数拼进 SQL 的路径（含 ORM 原生入口）？
  反序列化入口是否限制了可还原的类型？

### 4. XSS

- **MUST** 让所有输出到浏览器的不可信数据按输出上下文编码，**MUST NOT** 拼接 HTML。
- **MUST** 使用模板引擎的默认转义；显式关闭转义的地方 MUST 逐个说明理由并做白名单净化。
- **MUST** 按上下文区分编码：HTML 文本、属性、URL、JavaScript、CSS 各不相同。
- **MUST NOT** 把不可信数据直接写入 `innerHTML`、`dangerouslySetInnerHTML`、
  `v-html`、`eval`、`new Function` 或内联事件属性。
- **SHOULD** 设置 Content-Security-Policy，避免依赖内联脚本；
  富文本 SHOULD 使用经过验证的净化库并配置白名单，
  **MUST NOT** 自行写正则过滤 `<script`。
- 判断依据：新增的渲染路径是否有「绕过转义」的写法？是否有 CSP？

### 5. CSRF

- **MUST** 让任何会改变状态、且基于浏览器隐式凭据（Cookie）的请求都有 CSRF 防护。
- **MUST NOT** 让 `GET`/`HEAD` 产生副作用，也 MUST NOT 把状态变更放进「看起来只是查询」的接口。
- **SHOULD** 使用框架自带的 CSRF Token 并校验，或采用 `SameSite` + 来源校验的组合策略。
- **SHOULD** 对状态变更接口校验 `Origin` / `Referer`（在可用时）并拒绝跨站来源；
  **SHOULD NOT** 把 `Referer` 单独当作 CSRF 防护，它只作为附加校验。
- 若改用 Bearer Token 且不通过 Cookie 自动携带，**MUST** 在文档中说明 CSRF 风险如何消除。
- 判断依据：新增的 POST/PUT/PATCH/DELETE 接口是否覆盖 CSRF 防护？

### 6. SSRF 与外部 URL 检查

- **MUST NOT** 让用户直接控制服务端代表用户发起的请求目标。
- **MUST** 对目标做严格白名单（域名/IP/端口/协议），**MUST NOT** 允许
  `file://`、`gopher://` 等非常规协议。
- **MUST** 在**每次实际连接前**解析并校验 IP，拒绝环回、链路本地、私有网段与云元数据地址，
  以防 DNS rebinding 与重定向绕过。
- **MUST NOT** 跟随不受控的重定向；**SHOULD** 限制重定向次数与目标。
- **MUST** 让出站请求设置连接/读取超时与响应大小上限；
  **MUST** 对用户提供的路径与文件名做安全检查，见 §11。
- **MAY** 在受控环境中通过显式配置的代理出站，
  但 **MUST NOT** 因此跳过目标白名单与每次连接前的 IP 校验。
- 判断依据：URL 参数是否经过白名单？DNS 解析到内网地址时是否被拒绝？

### 7. 命令注入

- **MUST NOT** 把不可信数据交给 shell 解释。
- **SHOULD** 优先使用语言自身的 API 完成任务，不调用外部命令。
- 必须调用时，**MUST** 使用参数数组形式（不拼接命令字符串、不启用 `shell=True`）。
- **MUST** 把可执行文件路径固定为服务端常量，参数使用白名单或严格校验；
  **MUST NOT** 把用户输入作为命令名、选项名、环境变量名或路径片段。
- 判断依据：搜索 `exec` / `system` / `subprocess` / `child_process` 调用点，
  是否有拼接或 shell 模式？

### 8. 敏感信息与敏感配置管理

- **MUST NOT** 把密钥、口令、Token、私钥、连接串写入代码、配置文件或版本库；
  **MUST NOT** 在日志、文档和测试数据中泄露真实密钥。
- **MUST** 通过环境变量、密钥管理服务或运行时注入获取；
  示例配置 **MUST** 只使用明显虚构的无效凭据。
- **MUST NOT** 将敏感信息返回给无权访问的用户。
- **SHOULD** 只收集完成业务所必需的数据，**MUST NOT** 收集不必要的个人信息。
- **SHOULD** 对传输中的敏感数据采用加密保护。
- **MUST** 在提交前检查 diff 中是否出现高熵字符串、私钥头、`AKIA` 类前缀；
  历史提交中一旦泄漏，MUST **轮换**密钥，仅删除文件不等于修复。
- **MUST** 让生产与测试/开发凭据隔离，**MUST NOT** 共用。
- 判断依据：新增配置项是否含真实凭据？日志与错误信息是否可能打印配置值？

### 9. 密码与 Token 处理

- **MUST NOT** 明文存储、记录日志或回显密码；
  **MUST** 使用带盐的慢哈希算法（Argon2id / bcrypt / scrypt），
  **MUST NOT** 用 MD5/SHA 家族直接哈希。
- **MUST** 让 Token 按最小有效期签发，包含明确的 issuer / audience / 过期时间；
  服务端 MUST 校验签名、算法、过期与受众。
- **MUST** 让密码重置、修改密码、敏感操作重新验证；
  重置 Token MUST 一次性、短时效、用后即失效。
- **MUST NOT** 在 URL、日志、Referer 可达位置传递 Token；
  **SHOULD** 优先使用安全 Cookie 或授权头。
- **MUST** 为令牌注销/登出提供服务端失效机制。
- 判断依据：数据库中是否存过明文密码？Token 校验是否只验签名不验过期？

### 10. 日志脱敏与个人信息

- **MUST NOT** 在日志与错误信息中出现凭据、令牌、口令、身份证号、手机号、
  银行卡号、完整请求体或可还原的个人信息。
- **MUST** 建立字段级脱敏清单并在日志封装层统一实现，
  **MUST NOT** 依赖每个调用点自觉。
- **SHOULD** 需要关联时使用不可逆哈希或掩码（保留末 4 位），**MUST NOT** 输出完整值。
- **MUST** 在输出异常堆栈前过滤可能包含的敏感参数。
- **SHOULD** 让审计日志记录「谁、何时、对什么对象、做了什么、结果」，
  **MUST NOT** 记录敏感内容本身。
- 判断依据：新增日志语句是否可能打印整个对象/请求体？脱敏清单是否覆盖新增字段？

### 11. 文件上传与外部路径安全

- **MUST** 把上传内容视为不可信数据，从内容、名称、路径、大小、存储、访问六方面校验。
- **MUST** 以内容检测 / magic bytes 为主校验类型，
  **MUST NOT** 信任客户端提供的 `Content-Type` 与扩展名。
- **MUST** 限制大小与数量；解压类文件 MUST 限制条目数、总大小与路径穿越。
- **MUST** 由服务端生成存储文件名，**MUST NOT** 让用户提供的路径片段参与拼接，
  以阻止目录穿越；外部路径与文件名 MUST 做白名单/规范化校验。
- **MUST** 把上传文件存放在不可执行、非 Web 根可达的位置，访问时走带授权的读取接口。
- **SHOULD** 按需要重新编码或做病毒扫描，**MUST NOT** 以原始形式直接回显给用户。
- 判断依据：用户能否上传可执行文件并被服务端执行/直接访问？路径是否可被 `../` 影响？

### 12. 依赖和供应链

- **MUST** 让新增第三方依赖获得授权，并评估来源、维护状态、许可证与已知漏洞。
- **MUST** 使用可信来源的依赖；**MUST NOT** 引入来源不明、已弃维护、
  许可证冲突或需要执行安装脚本的依赖。
- **MUST NOT** 随意执行来源不明的脚本（下载即执行、未审查的安装脚本、
  复制粘贴的构建命令）。
- **SHOULD** 优先使用标准库或项目既有依赖，**MUST NOT** 为一个小功能引入大型依赖，
  见 [ai-behavior.md](ai-behavior.md) §3 与
  [engineering-principles.md](engineering-principles.md) §6。
- **MUST** 锁定版本（lock 文件）并纳入版本管理；**SHOULD** 定期检查已知漏洞，
  对间接依赖同样适用；**MUST NOT** 在生产环境自动拉最新版。
- 判断依据：本次改动是否新增依赖？是否说明了必要性与替代方案评估？

### 13. API 权限校验

- **MUST** 让每个接口在**服务端**独立完成认证、对象级授权与输入校验；
  **MUST NOT** 只依赖前端控制权限或前端隐藏。
- **MUST** 按「当前身份 + 目标对象 + 允许的操作」判定对象级授权（IDOR 防护），
  **MUST NOT** 只判定「已登录」或「拥有某角色」。
- **MUST** 让列表、导出、批量、管理端、内部接口、调试接口同样受本规则约束。
- **MUST NOT** 在返回体中包含调用方无权查看的字段；
  **SHOULD** 让错误信息不泄漏资源是否存在以外的信息。
- **SHOULD** 使用限流与配额防滥用与枚举，但 **MUST NOT** 用它替代授权。
- 契约细节见 [../standards/backend/api.md](../standards/backend/api.md)，
  认证实现见 [../standards/backend/authentication.md](../standards/backend/authentication.md)。
- 判断依据：把资源 ID 换成他人 ID 是否仍能读/写？批量接口是否逐个校验对象权限？

### 14. 多租户数据隔离

- **MUST** 让租户隔离由服务端在数据访问层强制，
  **MUST NOT** 依赖调用方传入正确的租户 ID。
- **MUST** 让每条查询与写入都带租户条件；租户上下文 MUST 来自可信身份，
  **MUST NOT** 来自请求参数。
- **SHOULD** 提供统一的数据访问层或数据库级隔离机制，避免每个接口各自实现而遗漏。
- **MUST** 让缓存键、消息队列 topic、文件名、导出任务、搜索索引同样包含租户维度。
- **MUST** 为隔离写专门测试：用租户 A 的身份尝试读写租户 B 的数据，MUST 被拒绝。
- **SHOULD** 让跨租户的管理/运营能力单独授权并留审计日志。
- 判断依据：新增的查询是否遗漏租户条件？缓存与异步任务是否携带租户上下文？

### 15. 安全变更

涉及认证、授权、密码、密钥、支付、用户数据等敏感逻辑时：

- **MUST** 检查完整调用链（入口 → 业务层 → 数据访问层 → 返回体），
  **MUST NOT** 只改最外层的一个判断就宣称修复完成。
- **MUST** 考虑越权路径与异常路径：权限不足、凭据过期、资源不存在、
  并发冲突、部分成功时是否仍安全。
- **MUST** 补充必要的安全测试（至少覆盖未认证、越权身份、跨租户/跨对象访问），
  见 [testing-principles.md](testing-principles.md) §4。
- **MUST** 向用户说明高风险变更的影响面；涉及破坏性或不可逆操作时，
  按 [ai-behavior.md](ai-behavior.md) §3 取得明确授权。
- **SHOULD** 在报告中单列「安全影响」一节，写明是否扩大/缩小了权限面。
- 判断依据：安全改动是否附带测试？测试是否包含「换一个身份/租户必须被拒绝」的断言？

## 禁止事项

索引式汇总（规则正文见对应章节，此处不重复定义）：

- **MUST NOT** 把认证与授权合并、默认信任客户端身份、只依赖前端权限控制（§1、§13）。
- **MUST NOT** 拼接 SQL / 命令字符串、对不可信数据做不安全反序列化、
  让用户直接控制出站请求目标或路径片段（§3、§6、§7）。
- **MUST NOT** 绕过 HTML 转义、把不可信数据写入 `innerHTML` / `v-html` / `eval`，
  或让 `GET` 产生副作用（§4、§5）。
- **MUST NOT** 在代码、配置、日志、文档、测试数据中放入真实密钥；
  **MUST NOT** 向无权用户返回敏感信息（§8、§9、§10、§13）。
- **MUST NOT** 信任客户端提供的 `Content-Type` / 扩展名 / 文件名，
  或把上传文件放在可执行、Web 根可达的位置（§11）。
- **MUST NOT** 引入来源不明/需执行安装脚本的依赖，
  或随意执行来源不明的脚本（§12）。
- **MUST NOT** 依赖调用方传入正确租户 ID，或让租户条件出现在部分查询中（§14）。
- **MUST NOT** 在未检查完整调用链、未补安全测试的情况下交付敏感逻辑变更（§15）。

## 验收要求

- [ ] 把用户 A 的 ID 换成 B 的 ID，接口拒绝返回 B 的数据（§1、§13）。
- [ ] 新增 POST/PUT/PATCH/DELETE 接口有 CSRF 防护；`GET`/`HEAD` 无副作用（§5）。
- [ ] 搜索仓库无「请求参数拼进 SQL / 命令」的路径（含 ORM 原生入口）（§3、§7）。
- [ ] 出站 URL 白名单 + 每次连接前 IP 校验就绪，重定向受控（§6）。
- [ ] 上传路径使用服务端生成的文件名，`../` 无法影响存储位置（§11）。
- [ ] diff 中无真实凭据、私钥头、高熵字符串；示例配置只含虚构值（§8）。
- [ ] 日志脱敏清单覆盖新增字段；异常堆栈输出前已过滤（§10）。
- [ ] 新增依赖有授权、来源、维护状态、许可证与漏洞评估记录（§12）。
- [ ] 存在「租户 A 读写租户 B 数据必须被拒绝」的测试（§14）。
- [ ] 敏感逻辑变更附带越权/异常路径的安全测试，报告含「安全影响」一节（§15）。
- [ ] 违反任何 `SHOULD` / `SHOULD NOT` 时已写明理由（[README.md](README.md) §2）。
