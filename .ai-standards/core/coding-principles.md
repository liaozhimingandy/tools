# 编码原则

> **规范用语**：定义见 [README.md](README.md) §2；**冲突处理规则**以
> [README.md](README.md) §4 为唯一权威。
> **前提**：[engineering-principles.md](engineering-principles.md) §8–§10 定义异常处理、
> 日志、配置与安全边界的**策略层**；本文件只定义**代码怎么写**，不复述策略。
> 语言专属细则见 [../standards/languages/](../standards/languages/)。

**与 `standards/` 的关系**：`standards/` 在不违反 `core/` 原则的前提下细化具体做法；
若两者冲突，以 `core/` 为准并修正 `standards/`，安全红线见
[security-principles.md](security-principles.md)，完整规则见 [README.md](README.md) §4。

---

## 文档目的

定义与具体语言无关的通用编码规范，使 AI 写出的代码能被下一个维护者读懂、
能定位失败、能被测试、不会把环境差异或敏感信息硬编码进源码。
本文件回答「代码应该长什么样」，不回答「系统应该怎么分层」。

---

## 适用范围

适用于所有语言的代码级写法：新增函数/类、修改现有实现、重构局部逻辑、
编写示例代码、提交前自检。不适用于：模块划分与依赖方向
（见 [architecture-principles.md](architecture-principles.md)）、
测试分层（见 [testing-principles.md](testing-principles.md)）、
具体语言的惯用写法（见 [../standards/languages/](../standards/languages/)）。

---

## 核心规范

### 1. 可读性优先

- **MUST** 让代码首先写给下一个维护者读，其次才是给机器执行。
- **MUST** 使用能表达真实业务含义的名字；**SHOULD NOT** 使用
  `data`、`info`、`tmp`、`handle`、`flag` 这类无信息量命名（循环变量 `i`、
  约定俗成的缩写除外）。
- **MUST NOT** 使用不必要的缩写；**MUST** 让命名风格与所在仓库/语言既有风格一致，
  **MUST NOT** 因个人偏好引入第二套风格。
- **SHOULD** 让布尔变量与函数用能读出真假问题的名字（`isActive`、`hasPermission`），
  **SHOULD NOT** 使用否定式双重取反。
- **MUST NOT** 散落魔法数字与魔法字符串；出现时 MUST 给语义名或注释说明来源。
- **MUST** 让注释解释原因、约束、复杂逻辑，**MUST NOT** 用注释复述代码在做什么。
- 判断依据：不看实现，仅凭命名能否猜出函数做什么、返回什么？删掉注释后非直觉之处是否仍可理解？

### 2. 命名一致

- **MUST** 让同一概念在全仓库使用同一个词，不同概念不用同一个词。
- **MUST** 先查项目已有的术语表、类型名和字段名，再决定新名字。
- **MUST NOT** 为了「更标准」批量重命名既有公开命名，见
  [engineering-principles.md](engineering-principles.md) §4。
- **SHOULD** 只使用项目已接受的缩写，**MUST NOT** 新造缩写。
- 判断依据：新增命名是否与同模块已有命名表达同一概念？

### 3. 代码组织与函数

- **MUST** 把相同职责的代码放在同一模块/文件内；**MUST NOT** 做无意义的文件拆分
  或创建没有实际价值的抽象。
- **MUST** 保持控制流线性、分支浅、副作用显式；一个函数只做一件事。
- **SHOULD NOT** 写过长的函数与复杂条件嵌套；**SHOULD** 用早返回（guard clauses）减少嵌套。
- **MUST** 让函数若修改外部状态或执行 I/O，在命名或文档中体现，不留隐式副作用。
- **SHOULD** 参数过多时先检查职责是否过载，再考虑结构化参数对象，
  **SHOULD NOT** 堆叠一堆可选参数。
- **MUST NOT** 复制粘贴后微调；重复逻辑按
  [engineering-principles.md](engineering-principles.md) §3 处理。
- **MUST** 保持项目原有代码风格，不顺手做整文件格式化。
- 判断依据：函数是否同时做了「计算」和「写入」？分支嵌套是否超过 3 层？
  本次 diff 是否出现与需求无关的纯格式改动？

### 4. 类型与数据形状

- **MUST** 让非法状态尽可能无法被表示。
- **SHOULD** 在有类型系统的语言开启严格模式，**MUST NOT** 用
  `any` / 裸 `dict` / 无类型集合回避建模；与第三方边界确有必要时，
  MUST 在边界上立即转换为明确类型。
- **SHOULD** 用枚举/字面量联合表达有限取值，**MUST NOT** 用裸字符串比较状态。
- **MUST** 区分「值不存在」「值为空」「未加载」三种语义，不都塞进 `null`。
- **SHOULD** 在边界处校验输入输出的数据形状，见
  [../standards/backend/api.md](../standards/backend/api.md)。
- 判断依据：新增字段是否有明确类型与取值约束？是否用哨兵值表达业务状态？

### 5. 错误处理的代码写法

策略见 [engineering-principles.md](engineering-principles.md) §8；本节只约束写法。

- **MUST** 捕获具体异常类型；**MUST NOT** 使用空捕获块、捕获后只打日志就继续执行、
  或用「捕获所有异常再断言不抛错」掩盖失败。
- **MUST** 让异常在能真正处理的层级处理，不能处理的向上传播并保留原始上下文。
- **MUST** 包装异常时保留原始异常作为 cause，不丢栈。
- **MUST** 让错误信息写清「什么操作、对哪个对象、因何失败」，足以定位问题，
  且**MUST NOT** 含敏感数据，见 [security-principles.md](security-principles.md) §10。
- **MUST NOT** 通过返回虚假成功结果掩盖失败；
  **SHOULD NOT** 用异常表达「正常但没找到」的业务结果，应返回明确的空值/结果类型。
- 判断依据：是否存在 `except: pass` 一类写法？失败后是否继续使用了未初始化的变量？

### 6. 注释与文档字符串

- **MUST** 让注释解释「为什么」，代码本身解释「做什么」。
- **MUST NOT** 写复述代码的注释（`// i++`）、过期注释，或注释掉大段代码留作「备份」。
- **MUST** 在以下情况写清「为什么」：非直觉的算法选择、业务例外、兼容历史行为、
  临时绕过（并标注解除条件）、与安全相关的约束。
- **SHOULD** 为公开接口写文档字符串：用途、参数、返回、可能抛出的错误、边界条件。
- **MUST NOT** 在正式交付里留裸 `TODO` / `FIXME`；确需保留时 MUST 附可追踪标识与上下文。
- 判断依据：删掉所有注释后，非直觉之处是否仍能被理解？

### 7. 输入校验与边界写法

- **MUST** 让校验发生在边界，内部逻辑信任已校验的数据。
- **MUST NOT** 在每一层重复校验同一条件；内部函数通过类型与不变量保证前提。
- **MUST** 让外部输入校验覆盖类型、范围、长度、格式、枚举取值、集合大小。
- **MUST** 让校验失败返回一致、可机读的错误结构，**MUST NOT** 泄漏堆栈、内部路径或敏感信息。
- 安全相关细则见 [security-principles.md](security-principles.md)。
- 判断依据：外部输入是否在进入业务逻辑前被校验？

### 8. 并发与时间

- **MUST** 让并发与时间的假设显式，**MUST NOT** 依赖「通常不会」。
- **MUST** 为共享可变状态指定明确的同步策略，或改为不可变数据。
- **SHOULD** 使用统一的时区与时钟来源；**MUST NOT** 依赖本地时区做业务判断。
- **MUST** 在调用外部系统时显式设置超时、重试、幂等键，不依赖默认值。
- **MUST NOT** 使用 `sleep` 作为同步手段，或在循环里无条件重试。
- 判断依据：并发执行时是否会产生重复写入？时区/夏令时是否影响业务日期？

### 9. 可测试性

- **MUST** 让核心业务规则不依赖具体 I/O 就能被测试。
- **SHOULD** 通过参数或接口注入依赖（时钟、随机、网络、数据库、文件系统），
  **MUST NOT** 在函数内部直接构造这些依赖。
- **SHOULD** 把核心业务规则放在纯函数或无副作用组件中，I/O 放在薄适配层。
- 具体测试分层与 Mock 边界见 [testing-principles.md](testing-principles.md)。
- 判断依据：能否在不启动服务、不连数据库的情况下测试这条业务规则？

### 10. 提交前的代码级自检

按序检查，逐条可勾选（**MUST** 实际执行，不得凭印象勾选）：

1. 无未使用的导入、变量、参数、死分支。
2. 无调试输出、临时开关、硬编码的环境值或密钥。
3. 命名与仓库既有风格一致，术语统一。
4. 错误路径与边界条件已处理，异常未被吞掉。
5. 新增/修改的公开契约已有文档字符串与测试。
6. 没有与本次需求无关的格式化或重命名 diff。
7. 静态检查、类型检查、格式化检查、构建均通过，且是**实际运行**过的。
8. 与 [ai-behavior.md](ai-behavior.md) 的汇报要求一致：如实说明跑了什么、结果如何。

- **MAY** 用项目既有的 lint / 格式化工具自动化第 1–3 项；
  **MUST NOT** 用工具输出代替对第 4–8 项的人工确认。

### 11. 日志（代码写法）

策略与级别语义见 [engineering-principles.md](engineering-principles.md) §9、
脱敏要求见 [security-principles.md](security-principles.md) §10；本节只约束写法。

- **MUST** 让关键业务流程的入口、成功与失败分支都有日志，日志带必要上下文（稳定事件名 + 可关联标识）。
- **MUST NOT** 输出敏感数据、完整请求体/响应体或大对象。
- **MUST** 让错误日志有助于问题排查：写清操作对象与失败原因，而不是 `"failed"`。
- **SHOULD NOT** 输出大量无价值日志（循环内的 `INFO`、逐字段打印对象）。
- **MUST NOT** 用「记录一条日志」代替异常处理或传播，见
  [engineering-principles.md](engineering-principles.md) §8。
- 判断依据：新增日志语句是否可能打印整个对象？级别是否正确？是否有稳定可检索的事件名？

### 12. 配置管理（代码写法）

策略见 [engineering-principles.md](engineering-principles.md) §10；本节只约束写法。

- **MUST** 让配置读取集中在一处，业务逻辑通过明确的接口取得配置值，
  **MUST NOT** 在函数体内散落读取环境变量或硬编码环境相关值。
- **MUST NOT** 把密钥、Token、口令写进源码、示例配置或测试数据，见
  [security-principles.md](security-principles.md) §8。
- **MUST** 让默认配置安全（不开放高权限、不启用调试开关、不使用弱口令）；**MUST** 让配置错误尽早被发现并明确报告，
  **MUST NOT** 静默回退到不安全的默认值。
- **SHOULD** 对新增配置项做类型与取值范围校验，并写明用途、默认值、生效范围。
- 判断依据：新增配置项是否在启动时被校验？示例配置是否只含虚构凭据？

### 13. 资源管理

- **MUST** 正确释放文件句柄、网络连接、数据库会话、锁等资源；
  **MUST** 使用语言提供的确定性释放机制（`with` / `try-with-resources` / `defer` / `using`）。
- **MUST NOT** 在异常路径上泄漏资源；**SHOULD** 通过测试覆盖「获取资源后中途失败」的场景。
- **SHOULD NOT** 做不必要的重复初始化（循环内反复建连接、每次调用都重新解析配置）。
- **MUST** 对并发与共享资源保持谨慎：锁的范围、顺序与超时 MUST 明确，
  **MUST NOT** 依赖「通常不会同时发生」。
- 判断依据：长时间运行后连接/句柄数是否持续增长？异常路径是否仍会释放？

## 禁止事项

索引式汇总（规则正文见对应章节，此处不重复定义）：

- **MUST NOT** 使用无信息量命名、不必要缩写、魔法值、复述代码的注释（§1、§6）。
- **MUST NOT** 因个人偏好引入第二套命名风格、批量重命名既有公开命名、
  做无意义文件拆分或整文件格式化（§2、§3）。
- **MUST NOT** 静默吞掉异常、用宽泛捕获掩盖错误、返回虚假成功结果、
  在错误信息中泄漏敏感数据（§5、§7）。
- **MUST NOT** 硬编码环境配置或密钥、让配置错误静默回退（§12）。
- **MUST NOT** 输出敏感日志、用日志代替错误处理（§11）。
- **MUST NOT** 在异常路径泄漏资源、用 `sleep` 做同步、依赖本地时区做业务判断（§8、§13）。
- **MUST NOT** 在正式交付里留裸 `TODO` / `FIXME`（§6）。

## 验收要求

- [ ] 命名与仓库既有风格一致，无无信息量命名、魔法值、新造缩写（§1、§2）。
- [ ] 无与需求无关的纯格式 diff；无无意义文件拆分或无价值抽象（§3）。
- [ ] 分支嵌套 ≤3 层，函数未同时承担「计算」与「写入」（§3）。
- [ ] 无空捕获块 / 宽泛捕获；失败路径错误信息可定位且不含敏感字段（§5、§7、§11）。
- [ ] 公开契约有文档字符串、类型约束与测试；非法状态无法被表示（§4、§6、§9）。
- [ ] 新增配置项集中读取、已校验、默认值安全，示例配置只含虚构凭据（§12）。
- [ ] 资源在异常路径上仍被确定性释放；并发写入不会重复（§8、§13）。
- [ ] §10 的 8 项自检已逐条实际执行，静态检查/类型检查/构建有真实输出（§10）。
- [ ] 违反任何 `SHOULD` / `SHOULD NOT` 时已写明理由（[README.md](README.md) §2）。
