# 通用工程原则

> **规范用语**：MUST / MUST NOT / SHOULD / SHOULD NOT / MAY 的定义见
> [README.md](README.md) §2；**冲突处理规则**以 [README.md](README.md) §4 为唯一权威。
> **定位**：设计层与项目治理层原则。代码级写法见 [coding-principles.md](coding-principles.md)，
> 系统结构见 [architecture-principles.md](architecture-principles.md)，
> AI 行为红线见 [ai-behavior.md](ai-behavior.md)。

---

## 文档目的

定义整个软件工程体系中**与语言、框架、工具、业务项目都无关**的基本取舍与治理原则，
使 AI 在面对「该改多少、该不该复用、能不能换技术、要不要兼容旧行为」这类问题时，
有可判断对错的依据，而不是依赖个人偏好。每节末尾的「判断依据」是
`code-review` Skill 与人工评审的核对点。

---

## 适用范围

适用于**所有**编程语言、技术栈、项目与 AI 编程工具的每一次代码或配置改动。
不适用于：具体语言/框架的用法（见 [../standards/](../standards/)）、
代码级写法细节（见 [coding-principles.md](coding-principles.md)）、
AI 自身行为的红线（见 [ai-behavior.md](ai-behavior.md)）。

---

## 核心规范

**总纲（工程质量取舍）**

- **MUST** 把正确性置于开发速度之前：不能通过跳过验证、吞掉错误或绕过测试来换取更快交付。
- **MUST** 把可维护性置于短期代码数量之前：新增代码量本身不是进展的证据。
- **MUST** 在没有明确证据表明简单方案不足时，选择能被一遍读懂的最直接实现。
- **SHOULD** 优先采用成熟、稳定、经过验证且文档完善的技术，而不是新出现的方案；
  选择新方案时 MUST 在方案说明中写出理由与已知风险。
- **MUST NOT** 为了「看起来专业」引入过度设计、过度抽象或额外的间接层。
- 判断依据：删掉本次新增的某一层/参数/配置项后，需求是否仍能完成？若「能」，该层就是多余的。

### 1. 单一职责（SRP）

- **MUST** 让一个模块、类或函数只承担一个变更理由；若两个互不相关的业务需求都会迫使它修改，就拆开。
- **SHOULD NOT** 把「步骤多」当成「职责多」：流程编排函数可以调用多个单一职责的组件。
- 判断依据：用一句话描述职责；出现「并且 / 同时 / 以及」通常已违反。
  新增文件的顶部说明能否用一句话写清唯一职责？

### 2. 高内聚、低耦合

- **MUST** 把相互依赖的代码放在同一边界内，跨边界只通过明确、稳定的接口通信。
- **MUST NOT** 让边界之外读取另一模块的内部状态，或把内部实现细节泄漏到边界之外。
- **SHOULD** 优先通过参数与返回值传递数据，避免共享可变全局状态与隐式依赖。
- **MUST** 保持依赖方向单向、无环，见 [architecture-principles.md](architecture-principles.md) §2。
- 判断依据：修改模块 A 的内部实现，是否需要同步改模块 B 的代码？跨模块调用是否只经过公开接口？

### 3. DRY / KISS / YAGNI

| 原则 | 要求 | 边界 |
| --- | --- | --- |
| DRY | **MUST** 让同一条**业务规则**只在一处定义 | 重复的是知识，不是长得像的代码；**SHOULD NOT** 为消除三行相似代码造出抽象层 |
| KISS | **MUST** 优先选择读一遍就能看懂的实现 | 简单不等于粗糙；仍须满足错误处理与安全要求 |
| YAGNI | **MUST NOT** 为「以后可能要」预埋开关、钩子、泛型参数或配置项 | 只实现当前需求明确要求的能力 |

- **SHOULD** 先写最直接满足验收标准的实现；只有当同一知识第三次重复、
  或需求明确要求扩展点时，才引入抽象。
- 判断依据：是否存在未被任何调用点使用的参数、配置项、接口或分支？
  新增抽象是否有至少两个真实调用场景？

### 4. 最小必要修改

- **MUST** 把改动范围限定在完成需求并通过验收所必需的代码内，优先解决用户明确提出的问题。
- **MUST NOT** 擅自重构无关模块、批量重命名、替换现有技术方案、删除原有功能或改变已有行为。
- **MUST NOT** 因个人偏好替换项目已采用的技术、风格或依赖。
- **SHOULD NOT** 把「行为变更」与「格式化 / 重命名 / 依赖升级」混在同一次改动中；
  确需混合时 MUST 在报告中说明理由。
- **SHOULD** 把顺手发现的技术债务记入报告，而不是顺手修掉。
- **MAY** 在同一改动里修正与本需求直接相关的拼写错误，
  但 **MUST NOT** 借此把改动扩大到无关文件的格式化或重命名。
- 判断依据：提交前逐文件回答「这个文件为什么在本次改动里」；答不上来的文件应移出改动集。
  `git diff --stat` 中是否存在整文件级别的纯格式 diff？

### 5. 优先复用现有实现

- **MUST** 在写新实现之前，按「同模块 → 同仓库公共层 → 已声明依赖 → 标准库 → 新增依赖」的顺序查找等价能力。
- **MUST** 复用前实际读取实现，确认行为、错误语义与边界条件匹配；**MUST NOT** 凭函数名猜测。
- **SHOULD** 当现有实现有缺陷时，在原位置做最小修复并补测试，而不是复制一份「修正版」。
- **MUST NOT** 重复引入项目中已有的同类功能。
- 判断依据：新增的工具函数是否与仓库中已有函数功能重叠？

### 6. 避免过度设计

- **MUST NOT** 引入当前问题不需要的层、模式、框架、配置项和间接调用。
- **MUST NOT** 为了「使用设计模式」而增加抽象；模式是对已存在问题的命名，不是设计目标。
- **MUST NOT** 引入仅有一个实现的接口、仅有一个消费者的事件总线、
  只有一层转发的包装层、只有一处读取的配置项。
- **MUST NOT** 为一个简单需求引入大型框架；新增第三方依赖 MUST 有明确理由并获得授权，
  见 [ai-behavior.md](ai-behavior.md) §3。
- 判断依据：删掉这一层，需求是否仍能完成？若「能」，这一层就是多余的。

### 7. 明确模块边界

- **MUST** 为每个模块写明公开接口、数据归属与不变量。
- **MUST NOT** 未经授权变更公开接口的签名、语义、错误码或返回结构，见本文 §13 与
  [ai-behavior.md](ai-behavior.md) §3。
- **MUST** 保证一份数据只有一个写入方；其他模块通过接口读取或发起变更请求。
- **MUST** 在边界上校验输入，并把边界错误转换成调用方能理解的语义。
- **SHOULD** 让重要业务逻辑处在清晰边界内，而不是散落在工具函数与回调里。
- 判断依据：模块是否有明确入口？跨边界调用是否绕过校验？

### 8. 异常处理

- **MUST** 只捕获能真正处理的异常；不能处理的向上传播并保留原始上下文。
- **MUST NOT** 静默吞掉异常：空 `except`/`catch`、捕获后仅打印不处理、
  用异常做正常控制流、捕获宽泛基类来「保险」，都在禁止之列。
- **MUST** 让错误信息包含可定位的上下文（操作对象、关键标识），且**MUST NOT** 含敏感数据，
  见 [security-principles.md](security-principles.md) §10。
- **MUST** 确定性释放文件、连接、锁等资源；**MUST NOT** 通过返回虚假成功结果掩盖失败。
- **SHOULD** 只对明确的瞬时故障重试，并设次数上限与退避策略。
- 判断依据：是否存在被吞掉的异常？失败路径是否留下可观察信号（日志 / 返回码 / 指标）？

### 9. 日志规范

- **MUST** 使用结构化日志与稳定级别：`ERROR`（需人工介入）、`WARN`（异常但可继续）、
  `INFO`（关键业务节点）、`DEBUG`（开发期细节，生产默认关闭）。
- **MUST** 让每条日志带稳定事件名与可关联的请求/事务标识；
  **MUST NOT** 输出无上下文的 `"failed"`。
- **SHOULD NOT** 在循环内输出 `INFO` 及以上级别日志，或把完整请求体、响应体、大对象写进日志。
- **MUST** 对日志内容脱敏，见 [security-principles.md](security-principles.md) §10。
- **MUST NOT** 用日志替代错误处理：记录之后仍须按 §8 处理或传播。
- 判断依据：级别是否正确？是否含敏感字段？是否有稳定可检索的事件名？

### 10. 配置管理

- **MUST** 让配置与业务逻辑分离，配置来源单一、可追溯、有默认值校验。
- **MUST NOT** 硬编码环境相关配置（地址、端口、超时、开关）。
- **MUST NOT** 把密钥、Token、口令写入代码、配置文件或版本库，见
  [security-principles.md](security-principles.md) §8。
- **MUST** 启动时校验必需配置；缺失或非法时快速失败并给出明确错误，
  **MUST NOT** 带着默认值静默运行。
- **SHOULD** 让默认配置安全（不开放高权限、不启用调试开关）；新增配置项 MUST 同时写明用途、默认值、
  取值约束、生效范围、变更是否需要重启。
- 判断依据：是否有硬编码的环境相关值？新增配置是否已文档化并校验？

### 11. 安全边界

- **MUST** 把所有跨边界的数据视为不可信输入，在边界上完成校验与授权。
- **MUST** 区分认证与授权，并在**对象级**执行授权，见 [security-principles.md](security-principles.md)。
- **MUST NOT** 让安全相关逻辑依赖客户端校验或前端隐藏；服务端 MUST 独立校验。
- 判断依据：每个入口点是否都能回答「谁在调用、能操作哪个对象、输入是否合法」？
- 信任边界包括：HTTP 请求、消息队列、文件上传、数据库读取结果、
  第三方 API 响应、环境变量、命令行参数。

### 12. 文档维护

- **MUST** 让文档与代码同批次修改，**MUST NOT** 留下「以后再补」的过期描述。
- **MUST** 在改动公开接口、配置、数据结构或部署方式时同步更新对应文档。
- **MUST** 让一条信息只在一个文档位置定义，其他位置用相对链接引用。
- **MUST** 保证文档中的命令可直接执行、链接指向存在的文件。
- 详细约定见 [documentation-principles.md](documentation-principles.md)。
- 判断依据：本次改动是否让某个文档中的命令、字段或链接失效？

### 13. 向后兼容

- **MUST** 默认保持现有调用方、数据、配置与部署方式可用；破坏性变更 MUST 显式授权。
- **MUST** 在修改公开接口前检查现有调用方；**MUST NOT** 擅自修改签名、字段语义、状态码、错误码。
- **MUST** 在修改数据库结构前评估数据迁移影响，并同时给出迁移、回滚与数据兼容方案，
  见 [../standards/backend/database.md](../standards/backend/database.md) 与
  [ai-behavior.md](ai-behavior.md) §3。
- **MUST** 在修改配置格式前考虑已有配置的兼容性；**MUST** 明确说明破坏性变更的影响面。
- **MUST** 在需要迁移时提供可执行、可验证的迁移方案。
- **SHOULD** 采用「新增 + 并行 + 渐进淘汰」而不是「直接替换」。
- 判断依据：现有调用方在不改代码的情况下是否仍能工作？旧数据能否被新代码读取？

## 禁止事项

以下是本文全部 `MUST NOT` 条款的**索引式汇总**（只列主题，不重新定义规则，详见对应章节）：

- **MUST NOT** 为完成当前需求擅自删除既有功能、重构无关模块、改变已有行为（§4）。
- **MUST NOT** 因个人偏好替换项目既有技术方案或重复引入同类功能（§4、§5）。
- **MUST NOT** 引入过度设计、只有一个实现的接口、只有一个消费者的事件（§6）。
- **MUST NOT** 静默吞掉异常、返回虚假成功结果、用日志替代错误处理（§8、§9）。
- **MUST NOT** 硬编码环境配置、把密钥写进代码或版本库、带非法配置静默运行（§10）。
- **MUST NOT** 依赖客户端校验或前端隐藏作为安全控制（§11）。
- **MUST NOT** 擅自修改公开 API 契约、跳过迁移与回滚方案（§13）。
- **MUST NOT** 在规范正文中写「编写高质量代码」这类无法判断对错的空洞口号（§1 文档目的）。

## 验收要求

逐条核对，**MUST** 有可追溯的证据（diff、命令输出、评审记录），不得凭印象勾选：

- [ ] 改动集里每个文件都能追溯到需求或验收标准；无整文件级纯格式 diff（§4）。
- [ ] 未出现新的第三方依赖，或新增依赖已附理由与授权记录（§6、[ai-behavior.md](ai-behavior.md) §3）。
- [ ] 新增抽象有 ≥2 个真实调用点；未被使用的参数/配置项/分支为零（§3、§6）。
- [ ] 失败路径有可观察信号，无空捕获块，日志不含敏感字段（§8、§9）。
- [ ] 新增配置项已写明用途、默认值、约束、生效范围，并做启动校验（§10）。
- [ ] 现有调用方无需改代码仍可工作；若涉及数据结构变更，迁移/回滚/旧数据兼容三项齐全（§13）。
- [ ] 相关文档已同批次更新，命令与链接仍有效（§12）。
- [ ] 若违反了任何 `SHOULD` / `SHOULD NOT`，实施报告中已写明具体理由
      （用语规则见 [README.md](README.md) §2）。
