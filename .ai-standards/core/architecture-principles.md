# 架构原则

> **规范用语**：定义见 [README.md](README.md) §2；**冲突处理规则**以
> [README.md](README.md) §4 为唯一权威。
> **前提**：[engineering-principles.md](engineering-principles.md)（通用原则）。
> **红线**：[ai-behavior.md](ai-behavior.md)（未经授权不重构、不换技术栈、不加依赖）。
> 具体技术做法见 [../standards/](../standards/)，API 契约见
> [../standards/backend/api.md](../standards/backend/api.md)。

架构设计的目标是**让变化局部化**：一个需求变更，只应在一处修改、一处测试、一处部署。

---

## 文档目的

定义软件架构设计与架构变更的原则，使 AI 在新增模块、调整边界、做技术选型时，
先基于代码事实理解现状，再给出可比较、可回滚、可迁移的方案，
而不是直接生成一个「看起来更合理」的新结构。

---

## 适用范围

适用于新增模块或子系统、调整模块边界、技术选型与依赖变更、数据归属调整、
接口契约变更、引入扩展点。不适用于：单个函数内部的实现写法
（见 [coding-principles.md](coding-principles.md)）、具体框架的目录约定
（见 [../standards/](../standards/)）。

---

## 核心规范

### 1. 先理解现有架构，再提出方案

- **MUST** 基于代码事实描述现状，**MUST NOT** 基于想象或常见项目模板推断现状。
- **MUST** 在现状描述中至少覆盖：模块清单及职责、依赖方向、数据归属、关键调用链、
  外部系统、部署形态、已有约束与妥协。
- **MUST** 把无法确认的部分标为「待确认」，**MUST NOT** 用推测填补，见
  [ai-behavior.md](ai-behavior.md) §2。
- **SHOULD** 在提案中回答「这个改动落在现有哪个边界内」；答不上来说明边界尚未被理解。
- 判断依据：现状描述中的每条结论是否都能指向具体文件或调用点？

### 2. 依赖方向单向、无环、职责分离

- **MUST** 让依赖只从「易变层」指向「稳定层」，且**MUST NOT** 形成环依赖。
- **MUST** 把业务逻辑与基础设施实现（数据库、HTTP 客户端、消息队列、文件系统）分离，
  让基础设施成为可替换的实现细节，**MUST NOT** 让业务规则直接依赖它们。
- **MUST NOT** 让一个模块承担过多无关职责，或让模块之间形成不必要的强耦合。
- **SHOULD** 采用「接口/适配层 → 应用/用例层 → 领域/业务规则层」的方向；
  环依赖出现时通过提取共享契约或反转依赖解除，**MUST NOT** 靠「延迟导入」绕过。
- 判断依据：画出依赖图后是否存在双向箭头或环？新增 import 是否让方向反转？

### 3. 模块职责与数据归属

- **MUST** 为每个模块写出唯一的职责陈述，为每份可写数据指定唯一的所有者。
- **MUST** 明确模块之间的数据交换格式；**SHOULD** 对关键业务状态做显式建模，
  **MUST NOT** 用散落的字符串或魔法值表达状态。
- **MUST NOT** 重复维护同一业务数据，或让跨模块共享的可变状态成为隐性耦合。
- **MUST** 把数据归属与事务边界一起写清楚：谁负责一致性、谁负责失败补偿。
- **MUST NOT** 为了方便把「什么都放里面」的 utils / common / shared 目录变成新模块。
- 判断依据：同一张表 / 同一份状态是否有两个写入方？新增字段是否只有一个所有者？

### 4. 接口契约显式且稳定

- **MUST** 写明边界上的输入、输出、异常行为、错误语义、幂等性、超时与重试行为。
- **MUST NOT** 让对外契约暴露内部数据结构；内部模型变化不应迫使调用方改动。
- **SHOULD** 用可验证的形式（类型、schema、测试）描述契约，**MUST NOT** 只留在口头约定里。
- **MUST** 遵守最小暴露：只提供当前明确需要的能力。
- **MUST** 把契约变更按破坏性变更处理，见
  [engineering-principles.md](engineering-principles.md) §13。
- 判断依据：契约是否有对应测试？错误分支是否被明确定义？

### 5. 技术方案评估

- **MUST** 至少对「最小改动方案」与一个替代方案做同维度比较，再给出结论。
- **MUST** 让结论指向一个方案并写明理由，**MUST NOT** 以「各有优劣」结束。
- **SHOULD** 默认选择改动范围最小、依赖最少、回滚最容易的方案。

| 评估维度 | 必须回答 |
| --- | --- |
| 需求满足 | 是否覆盖全部验收标准与已知边界条件 |
| 改动范围 | 涉及哪些模块、文件、契约、数据 |
| 依赖 | 是否引入新第三方依赖；现有依赖能否覆盖 |
| 扩展与维护 | 未来同类需求能否在现有边界内完成；维护者需要多少背景知识 |
| 安全 | 是否新增信任边界、是否扩大权限面，见 [security-principles.md](security-principles.md) |
| 性能 | 是否引入新的 N+1、全量加载、同步阻塞或重复计算 |
| 回滚 | 出问题能否在不动数据的情况下退回 |
| 成本 | 实现、测试、迁移、文档的总体成本 |

- 判断依据：比较表是否填完整？结论是否与表中的事实一致？

### 6. 不为模式而模式

- **MUST** 让抽象来自已存在的重复，**MUST NOT** 让抽象来自对未来的想象。
- **MUST NOT** 为未来可能发生的需求提前建立复杂框架、
  引入只有一个实现的接口、只有一个消费者的事件、只有一层转发的包装。
- **SHOULD** 优先使用组合而不是继承；只在继承确实表达业务上的「是一种」关系时采用。
- **MUST NOT** 引入新框架、中间件或运行时组件，除非现有能力无法覆盖且已获授权。
- **SHOULD** 让分层数量以「能隔离变化」为限，**MUST NOT** 为「看起来专业」加层。
- 判断依据：删掉这一层，当前需求是否仍能完成？见
  [engineering-principles.md](engineering-principles.md) §3、§6。

### 7. 可扩展性与维护成本

- **MUST NOT** 在没有明确扩展需求时引入扩展点；扩展机制 MUST 有实际使用场景。
- **MUST** 为每个扩展点写文档并给出至少一个真实用例，否则删除。
- **MUST NOT** 过度通用化；**SHOULD** 保持核心模块稳定，把变化隔离在边缘。
- **SHOULD** 每增加一个间接层都说明它消除了哪个具体重复或耦合。
- 判断依据：新增扩展点是否有第二个使用者？删除它是否影响当前需求？

### 8. 安全性与性能在架构阶段考虑

- **MUST NOT** 把安全与性能留到「上线前再优化」。
- **MUST** 明确每个信任边界上的认证、授权、输入校验与审计，见
  [security-principles.md](security-principles.md)。
- **MUST** 明确多租户/多组织数据的隔离层级，且隔离 MUST 在服务端强制。
- **SHOULD** 明确数据规模假设：分页、批量上限、超时、并发模型、缓存一致性。
- **SHOULD** 明确外部依赖不可用时的降级行为与数据一致性影响。
- 判断依据：设计文档是否有「安全」与「性能/容量」两节并写出具体措施？

### 9. 数据流明确

- **MUST** 对关键用例画出从入口到持久化、再到响应的完整数据流，
  标注每步的输入形态、校验点、转换、写入方、事务边界、失败行为、可观测信号。
- **MUST** 明确同步与异步的分界，以及异步失败后的补偿。
- **MUST NOT** 出现「数据在某处被隐式修改」的路径。
- 判断依据：对于一次写操作，能否指出唯一写入点，以及失败时数据处于什么状态？

### 10. 记录设计决策

- **MUST** 为重要决策留下「问题 → 备选方案 → 选择 → 理由 → 后果 → 重新评估条件」。
- **MUST** 把记录随设计文档一起版本化，**MUST NOT** 只留在聊天记录里。
- **MUST** 让决策可推翻：写明什么条件下应重新评估。
- 记录对象：技术选型、边界划分、数据归属、破坏性变更、被放弃的方案。
- 判断依据：半年后接手的人能否不看对话历史理解「为什么这样设计」？

### 11. 输出物要求

架构设计 MUST 产出可审阅的文档，而不是一段口头结论：

1. 现状与约束（基于代码事实，标出待确认项）；
2. 问题定义与验收标准；
3. 模块职责与边界（含依赖方向、数据归属）；
4. 方案比较表（§5 维度）与结论；
5. 关键用例的数据流；
6. 安全与性能考量；
7. 迁移 / 回滚 / 兼容方案；
8. 设计决策记录（§10）。

执行流程见 [../skills/architecture-design/SKILL.md](../skills/architecture-design/SKILL.md)。

### 12. 架构变更流程

修改架构前 **MUST** 按顺序完成以下六步，缺一步不得进入实施：

1. **理解现有架构**：按 §1 列出模块、依赖、数据归属与约束；
2. **检查相关模块和依赖关系**：找出全部调用方与受影响契约；
3. **说明当前设计存在的问题**：用事实描述痛点，**MUST NOT** 用「不够现代」这类评价代替；
4. **说明拟采用的解决方案**：按 §5 给比较表与结论；
5. **评估兼容性和迁移影响**：写明调用方、数据、配置、部署的影响与回滚路径；
6. **对高风险变更先征求用户确认**：涉及破坏性变更、大规模重构、技术栈替换时，
   按 [ai-behavior.md](ai-behavior.md) §3 取得明确授权后再实施。

- **SHOULD** 把六步的结论写进设计文档；
  **SHOULD NOT** 因为改动「看起来很小」而省去第 1、2 步的现状确认。
  简单、可逆、局部的调整 **MAY** 合并第 3–5 步，但第 1、2、6 步不得省略。
- 判断依据：设计文档是否能逐条对应这六步？高风险变更是否有用户确认记录？

## 禁止事项

索引式汇总（规则正文见对应章节，此处不重复定义）：

- **MUST NOT** 基于想象推断现状、用推测填补未知、靠延迟导入绕过环依赖（§1、§2）。
- **MUST NOT** 让模块承担过多无关职责、依赖基础设施细节、共享可变状态、
  重复维护同一业务数据、新建「什么都放」的公共目录（§2、§3）。
- **MUST NOT** 让对外契约暴露内部结构、未经授权变更契约（§4）。
- **MUST NOT** 以「各有优劣」结束方案评估（§5）。
- **MUST NOT** 为未来想象中的需求引入抽象、框架、扩展点或过度通用化设计（§6、§7）。
- **MUST NOT** 把安全与性能推迟到上线前、让隔离依赖调用方自觉（§8）。
- **MUST NOT** 留下隐式修改数据的路径（§9）。
- **MUST NOT** 跳过架构变更六步中的第 1、2、6 步（§12）。

## 验收要求

- [ ] 现状描述每条都能指向具体文件/调用点，未知项标为「待确认」（§1）。
- [ ] 依赖图无环、无双向箭头；新增 import 未反转依赖方向（§2）。
- [ ] 每份可写数据只有一个写入方；关键状态已显式建模（§3）。
- [ ] 接口契约有类型/schema/测试，错误分支已定义（§4）。
- [ ] 方案比较表 8 个维度齐全且结论指向单一方案（§5）。
- [ ] 新增扩展点有文档与 ≥1 个真实用例；无只有一个实现的接口（§6、§7）。
- [ ] 设计文档含「安全」「性能/容量」两节及具体措施（§8）。
- [ ] 关键用例数据流标注了写入方、事务边界、失败行为（§9）。
- [ ] 设计决策记录含重新评估条件，且随文档版本化（§10）。
- [ ] 输出物 8 项齐全；架构变更六步可逐条对应，高风险变更有授权记录（§11、§12）。
- [ ] 违反任何 `SHOULD` / `SHOULD NOT` 时已写明理由（[README.md](README.md) §2）。
