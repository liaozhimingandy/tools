# 跨模块回归测试

> Phase 6 建立跨模块回归测试，回答一个关键问题：**门禁本身真的能发现问题吗？**
> 只跑一次"全绿"不足以证明检查有效，必须主动注入破坏，验证每一类检查都会亮红灯。
> 测试入口：`tooling/tests/test_regression.py`。

---

## 1. 为什么需要变异注入

质量门禁（见 [统一质量门禁](quality-gates.md)）若写错——比如某个检查函数被误删、
某条规则永远不成立——普通"全绿"运行无法暴露它，反而会给出虚假的安全感。
回归测试采用**变异测试（mutation testing）**思路：

1. 把真实规范仓库复制到一个临时目录（不碰真实仓库）；
2. 在副本里注入一处确定的破坏（改坏结构、删文件、制造版本漂移等）；
3. 用门禁跑这个副本，断言**对应分组确实报出 ERROR**（或普通模式 WARNING、strict 升级）；
4. 副本在 `tearDown` 中删除，不留痕迹。

这样既验证了"正确仓库能通过"，也验证了"错误仓库会被拦住"，两个方向缺一不可。

---

## 2. 七个核心变异场景

任务书要求覆盖七个跨模块场景，每个都对应一处"单一事实来源"被破坏后门禁应有的反应。

| # | 注入的变更 | 期望被哪组门禁发现 | 断言要点 |
| --- | --- | --- | --- |
| 1 | 破坏某份 core 规范的六段结构（删/改必需章节标题） | 公共规范 | core 分组报 ERROR |
| 2 | 新增一份未被任何索引/适配器/规范引用的孤儿 core 规范 | 公共规范 | 普通模式报 WARNING，strict 升级为 ERROR |
| 3 | 让某个 Skill 的引用或 frontmatter 失效 | Skills | skills 分组报 ERROR |
| 4 | 篡改适配器 `config` 声明，使其与代码常量漂移 | 适配器 | adapters 分组报 ERROR |
| 5 | 删除一份公共规范，制造关联引用失效 | 公共规范 | 删除 core 规范后关联引用应失效 |
| 6 | 修改 `VERSION`，制造各版本来源不一致 | 版本管理 | version 分组报 ERROR |
| 7 | 删除安装器安全模块或删除适配器源文件 | 安装器 / 适配器 | 安装计划或安全模块检查报 ERROR |

场景 2 特别体现 Phase 6 新增的 `check_core_mapping`：Phase 5 只检查"链接目标是否存在"，
不检查"每份 core 规范是否都被引用"。新增孤儿文件过去会静默漏过，现在普通模式给
WARNING、strict 模式升级为 ERROR。

---

## 3. 补充场景

除七个核心场景外，测试还覆盖两个边界：

### 3.1 新增文件纳入验证

在副本里新增一份带失效内部链接的 Markdown，断言门禁会把它纳入检查并报出无效引用。
这防止一种漏检：只校验"已知文件清单"，导致新增文件绕过检查。

### 3.2 干净副本的反向保护

每个用例的基线都是"未注入变更的干净副本应通过门禁"。这是变异测试的对照组——
若干净副本也失败，说明注入逻辑或门禁本身有问题，而不是"检查严格"。

## 4. 本地执行

```bash
# 运行全部跨模块回归场景
python -m unittest tooling.tests.test_regression -v

# 或纳入全量测试
python -m unittest discover -s tooling/tests -v
```

测试使用 `tempfile.TemporaryDirectory` 隔离，全程不修改真实仓库、不安装、不写真实 home。
运行时长主要来自多次复制整棵仓库目录与反复调用门禁，属于正常的验证成本。

---

## 5. 新增场景的约定

为回归测试增加场景时，遵循以下约定以保持可维护性：

1. **只改副本，不改真实仓库**：所有注入都作用于 `clone()` 返回的临时路径。
2. **断言具体分组**：用 `r.groups[QG.GATE_xxx].count(C.ERROR)` 定位到预期分组，
   而不是只看总数，避免"恰好别处报错"造成的假通过。
3. **普通模式与 strict 分别断言**：涉及 WARNING 升级的场景，先断言普通模式有 WARNING、
   strict 模式 `promoted > 0` 且 ERROR 增加。
4. **清理彻底**：副本由 `tearDown` 统一删除，不依赖单个用例手动清理。
5. **同步规则**：若新增了 strict 升级规则，在
   `tooling/validators/quality_rules.py` 加规则的同时补一个变异场景。

## 6. 与其他测试的分工

| 测试文件 | 关注点 | 是否会注入破坏 |
| --- | --- | --- |
| `test_regression.py`（本文件） | 门禁能否发现跨模块不一致 | 是，主动注入 |
| `test_quality_gate.py` | 门禁编排、分组选择、结果结构 | 是，针对单组 |
| `test_upgrade_compatibility.py` | 升级路径下安装器的用户文件保护与回滚 | 是，针对安装过程 |
| `test_release_artifact.py` | 发布归档的构建与自校验 | 是，针对归档 |

四者共同构成"正确路径 + 错误路径 + 升级路径 + 发布路径"的完整回归网。

---

## 7. 边界与已知限制

- 变异测试验证的是**门禁会不会报错**，不验证报错文案对最终用户是否足够清晰；
  文案可读性靠人工审查与 CLI 输出契约测试保证。
- 当前场景是确定性单点注入，不覆盖"多处同时被改"的组合故障；组合故障可由
  CI 的矩阵与全量测试兜底。
- 副本复制会忽略 `__pycache__`、`*.pyc`、`.ai-standards` 镜像，避免把安装残留
  带进验证、污染结论。
