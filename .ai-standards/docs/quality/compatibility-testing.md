# 安装器升级兼容性测试

> Phase 6 补上安装器从旧版本升级到新版本的兼容性验证，回答：**用户已经装过一次之后，
> 再升级会不会弄丢他的改动、误删他的文件，或留下一个半装好的残局？**
> 测试入口：`tooling/tests/test_upgrade_compatibility.py`。

---

## 1. 测试方法与隔离

每个用例在 `setUp` 中做两件事：

1. 把真实规范仓库复制到临时目录作为"可改的规范源"，这样能改 `VERSION`、改源文件内容、
   删源文件后再升级；测试里的 `REPO` 由 `__file__` 解析为这个 clone 根，跑的是 clone 自己的
   `install.py`。
2. 另建一个临时目录作为安装目标（`target`），模拟用户项目。

`tearDown` 删除两者。全局（`global`）作用域用例用 `--home` 指向临时逻辑 home，
**绝不触碰运行者的真实 home**。全程零真实写入、零网络。

---

## 2. 两套用户文件语义（最容易混淆的地方）

升级安全性建立在"区分谁的文件"之上。请先记住两条**不同**的规则：

| 对象 | 判定依据 | 默认升级 | `--force` 升级 |
| --- | --- | --- | --- |
| 用户改过的**托管文件**（manifest 已登记，但磁盘哈希与登记哈希不符） | manifest 登记 + SHA-256 比对 | 跳过并报冲突，保留用户改动 | 覆盖前先备份，再恢复为源内容 |
| 用户**自有文件**（不在 manifest 清单里，如用户自己写的 `AGENTS.md`） | 清单无登记、无归属证据 | 永不覆盖 | **仍然永不覆盖** |

一句话：**用户自有文件即使 `--force` 也不覆盖；用户改过的托管文件 `--force` 会先备份
再覆盖，备份里保留着用户的原始内容。** 备份写入 `<管理目录>/backups/<run_id>/`，并在
`manifest.backups` 登记目标、哈希、时间与 run_id。

早期曾把这两条混为一谈，误以为"`--force` 后用户改动仍在"；这是错的。正确的验证是：
默认升级保留改动；`--force` 升级后目标恢复源内容，而**备份文件**里能找到改动。

---

## 3. 九个覆盖场景

| # | 用例 | 验证的核心承诺 |
| --- | --- | --- |
| 1 | 未修改的托管文件可更新 | 源内容变化 + 升版本后 `--force` 能写回新内容，manifest 版本推进 |
| 2 | 用户改过的托管文件：默认保护 / `--force` 备份后覆盖 | §2 两条语义，且 `manifest.backups` 有对应记录 |
| 2b | 用户自有入口文件永不覆盖 | 即使 `--force`，清单外的 `AGENTS.md` 保持用户原文 |
| 3 | 新增文件能正确安装 | 新版本往规范源加文件，升级后该文件被安装并登记进 manifest |
| 4 | 已删除源文件不误删用户文件 | 源被删时升级保留已装文件、保留用户改动，报 stale 告警，manifest 仍登记 |
| 5 | 失败可回滚 | 向第 N 次 `atomic_write` 注入失败，事务回滚、无 manifest、无半成品残留 |
| 6 | Manifest 反映最终状态 | schema / installer_version / scope / tools / files 正确，且不含绝对路径 |
| 7 | global 升级隔离 | `--home` 逻辑 home 内升级、生成入口重渲染为新版本，真实 home 未被触碰 |
| 8 | 升级后仓库仍过门禁 | 端到端确认升级流程没有把规范仓库自身弄坏 |

---

## 4. 关键实现保障

测试能成立，依赖 Phase 5 安装器的几项安全机制，这里说明它们如何被验证：

### 4.1 事务与回滚

所有写入经过 `filesystem.Transaction`：写前记录"新建/替换"及原字节，任一步失败
（注入的 `OSError`）就 `rollback()`，只回收本次创建或替换的文件，不递归删除用户目录。
场景 5 断言回滚后目标目录里残留文件数为 0，且不留下"看起来成功"的 manifest。

### 4.2 归属判定不只看文件名

`manifest.classify` 同时要求 manifest 登记与 SHA-256 比对：清单登记即视为托管资产，
哈希不符判定为 `MODIFIED`；清单无登记则按用户文件保护。这样 Skills / 镜像文件
（逐字节复制、无归属标记）在重复安装时不会被误判成用户文件而反复跳过。

### 4.3 manifest 登记期望哈希

manifest 登记的是"安装器期望的哈希"，而非磁盘实际哈希。这样被用户改过的托管文件
下次仍能被 `classify` 判为 `MODIFIED`，而不是被当成新版本内容而误覆盖。

### 4.4 生成文件重渲染

global 入口等生成文件以 `version=GENERATED` 为源模板标记，安装时渲染真实 `VERSION`。
场景 7 断言升级后入口里的版本 token 已更新为新版本号，避免"包升级了、入口还写着旧版本"。

## 5. 本地执行

```bash
# 仅运行升级兼容性测试（约需一分钟，主要开销是多次复制仓库与安装）
python -m unittest tooling.tests.test_upgrade_compatibility -v

# 纳入全量测试
python -m unittest discover -s tooling/tests -v
```

用例对 Windows 短名路径、临时目录路径都做了适配；`--home` 隔离确保不会污染
`C:\Users\<用户>` 或 `~` 下的真实配置。

---

## 6. 与升级操作的关系

本测试验证的是安装器能力；真实用户执行升级的命令与注意事项见
[安装指南的更新/备份/卸载章节](../installation.md) 与
[版本与兼容性规则的升级与迁移](../versioning.md)。发布一个 MAJOR 版本前的
人工核对项见 [发布前检查清单](../release/release-checklist.md)。

简言之：自动化保证"升级机制本身不弄丢文件"，人工保证"这次升级的业务影响被理解"。
两者不可互相替代。
