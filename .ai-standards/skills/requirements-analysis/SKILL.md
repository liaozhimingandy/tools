# Requirements Analysis

**核心约束**：本 Skill 产出**需求规格**，不产出设计、不做技术选型、不修改代码。
所有假设必须显式标注，不得把假设写成需求。

> 本文件自包含：执行所需的红线已内联。完整规范可在项目根目录
> `.ai-standards/core/` 下按需查阅（`ai-behavior.md`、`engineering-principles.md`），
> 但**不依赖**这些文件即可完成本 Skill。
> **渐进加载**：仅当任务确需通用原则的细节时才读取上述 core 文件；涉及具体语言/框架
> 的写法时再读 `.ai-standards/standards/` 对应规范。**不假设能访问其它会话的上下文**，
> 一切以当前工作区实际文件与用户本轮输入为准。禁止写 `../../core/xxx.md` 这类链接。

## 前置约束（内联红线）

- 不得凭空假设文件、接口、数据库字段或依赖；涉及现状的判断必须实际确认。
- 遇到不明确或高风险的需求必须先澄清，澄清期间只做只读调研。
- 不得擅自扩大范围、删除既有功能、修改公共 API 契约或新增第三方依赖。
- 完成后的汇报必须包含：修改内容、验证结果、风险与未决项、后续动作。

## 触发场景

- 用户给出一个目标但缺少边界、异常场景或验收口径；
- 需求描述中出现「大概」「类似」「跟之前一样」等模糊表述；
- 新功能可能影响既有功能，需要先厘清影响面；
- 用户说「先梳理需求」「明确一下范围」「验收标准是什么」。

## 何时不使用

- 需求已明确且验收标准齐备（直接进入 `architecture-design` 或 `software-development`）；
- 用户要的是架构方案（用 `architecture-design`）、实现（用 `software-development`）
  或审查结论（用 `code-review`）；
- 只是一次性小改动、边界清晰，梳理需求反而增加负担；
- 用户要理解现有项目现状（用 `project-analysis`）。

**判断依据**：若问题涉及「到底要做什么、做到什么算完成」，用本 Skill；
若「做什么」已确定、只差「怎么做」或「做得对不对」，用其它 Skill。

## 适用范围

- 输入：用户的原始需求描述、可选的项目现状资料（可来自 `project-analysis` 报告）、
  可选的约束（合规、性能、兼容、时间）。
- 权限边界：只读调研 + 产出文档；不修改项目代码。
- 输出是**规格**，不是承诺：所有未确认项保留为待确认，不被"合理默认"悄悄消化。

## 与其它 Skill 配合

| 关系 | 说明 |
| --- | --- |
| 上游输入 | 可直接从用户原始需求开始；`project-analysis` 报告是可选的影响面输入 |
| 下游消费 | 需求文档与验收标准交给 `architecture-design`（设计输入）或 `software-development`（实现与测试输入） |
| 运行时依赖 | **无**。本 Skill 可独立调用并独立完成 |
| 典型组合 | 复杂任务按「分析 → 需求 → 设计 → 实施 → 审查」组合；需求已明确时可跳过本 Skill |

> 组合是**可选**的典型流程，不是强制顺序；用户已给明确需求时可直接进入下游 Skill。

## 执行步骤

1. **理解用户需求**：用一句话复述目标，并拆成「要达成的业务结果」与「交付物」；
   把用户原话中的关键措辞保留下来，避免改写后语义漂移。
2. **区分明确需求和假设**：建立两列表格。明确需求必须能追溯到用户原话；
   其余一律进入「假设」，并写明"若假设不成立会怎样"。
3. **识别边界条件**：对每个输入维度列出边界值与边界外值
   （空/零/最大值/超上限/重复/超时/时区/状态机初始态与终态）。
4. **识别异常场景**：依赖不可用、权限不足、并发冲突、部分成功、
   数据不存在、重复提交、外部系统超时；逐条写明期望行为。
5. **分析对已有功能的影响**：实际查看相关模块与调用方，列出受影响的接口、
   数据、配置、文档、测试、部署；标出可能的回归风险。
6. **明确验收标准**：写成可验证的条件（给定/当/则 或 可执行的检查项），
   每条都能被测试或人工检查判定真假；避免「体验更好」「尽量快」。
7. **识别需要用户确认的事项**：把假设、边界取舍、破坏性变更、
   高风险操作整理成**可回答的问题**（背景 + 选项 + 各自后果）。
8. **输出结构化需求文档**：按 [需求文档模板](assets/requirements-template.md) 组织；
   未完成确认的条目保持 `待确认` 状态，不假装已定。

## 输入要求

| 输入 | 必需 | 缺失时 |
| --- | --- | --- |
| 用户原始需求描述 | 是 | 停止并请求提供，不自行编造需求 |
| 项目现状资料 | 否 | 标注「未做现状调研」，涉及影响面的结论标为待确认 |
| 约束（合规/性能/兼容/时间） | 否 | 标为假设并列入待确认清单 |
| 既有需求/验收文档 | 否 | 明确写「未找到」，不假定其存在 |

## 输出要求

Markdown 需求文档，章节固定为：

1. 目标与用户原话摘录；
2. 明确需求表（编号、描述、来源）；
3. 假设表（编号、假设、不成立时的后果、确认方式）；
4. 范围：包含 / 明确不包含；
5. 边界条件清单；
6. 异常场景与期望行为；
7. 对既有功能的影响与回归风险；
8. 验收标准（编号、条件、判定方式）；
9. 待用户确认事项（可回答的问题）；
10. 状态：已确认 / 待确认 / 阻塞。

模板见 [assets/requirements-template.md](assets/requirements-template.md)。

## 质量检查

- [ ] 每条明确需求都能追溯到用户原话；
- [ ] 没有把假设混进明确需求表；
- [ ] 边界条件覆盖空值、上限、重复、状态边界；
- [ ] 异常场景包含依赖失败、权限不足、并发与重复提交；
- [ ] 影响面基于实际查看的模块，而非推测；
- [ ] 每条验收标准都能被判定真假，没有模糊措辞；
- [ ] 待确认问题是具体可回答的，不是「请确认一下」；
- [ ] 文档未包含技术选型结论或实现代码。

## 完成标准

- 8 个步骤全部执行，文档 10 个章节齐全；
- 所有假设、边界取舍与高风险项都已转化为待确认问题；
- 验收标准可被 `software-development` 直接用于编写测试；
- 项目代码零改动；汇报中包含未决项与后续动作。

## 异常情况处理

| 情况 | 处理 |
| --- | --- |
| 需求自相矛盾 | 并列写出两种解读与各自后果，作为阻塞项请求澄清，不自行选一种 |
| 用户描述过于简短 | 列出最小必要的问题集（不超过 5 条），每条附选项；不批量追问 |
| 无法读取项目现状 | 影响面章节标「未调研」，明确说明结论的局限 |
| 涉及破坏性变更或高风险操作 | 单列为阻塞项，说明必须先获得明确授权，不得默认继续 |
| 验收标准无法客观判定 | 改写为可观察行为 + 判定方式；仍无法判定的标为待确认 |
| 用户催促「先做再说」 | 保留待确认项并明确写出风险，不把假设写成已确认需求 |
