# Project Analysis

**核心约束**：本 Skill 全程**只读**。未经用户明确授权，不得修改、创建或删除项目中的任何文件。
分析结论必须来自实际读取到的内容；读不到的部分标为「未确认」，不得推测填充。

> 本文件自包含：执行所需的红线已内联在下方。完整规范可在项目根目录的
> `.ai-standards/core/` 下按需查阅（`engineering-principles.md`、`ai-behavior.md`），
> 但**不依赖**这些文件即可完成本 Skill。
> **渐进加载**：仅当任务确需通用原则的细节时才读取上述 core 文件；涉及具体语言/框架
> 的写法时再读 `.ai-standards/standards/` 对应规范。**不假设能访问其它会话的上下文**，
> 一切以当前工作区实际文件为准。禁止写 `../../core/xxx.md` 这类安装后会失效的链接。

## 前置约束（内联红线）

- 修改代码之前必须先理解现有项目；不得凭空假设文件、接口、数据库字段或依赖。
- 只读调研期间不得实施写操作，不得执行安装、迁移、构建写盘、提交、推送等有副作用的命令。
- 不确定处先标注「待确认」并向用户澄清，不用"最可能的猜测"填补。
- 报告中的事实必须可追溯到具体路径或命令输出；不得伪造。

## 触发场景

- 接手一个陌生仓库，需要在动手前了解结构与约定；
- 需求/架构/开发任务开始前的现状调研；
- 评估一次改动可能影响哪些模块与外部系统；
- 用户说「先看看这个项目」「梳理一下技术栈」「这个项目怎么组织的」。

## 何时不使用

- 已充分掌握项目且任务范围明确，无需再摸现状；
- 用户只要求直接修改某个已知文件（改用 `software-development`）；
- 需要的是技术选型或模块划分结论（改用 `architecture-design`）；
- 需要的是对既有改动的审查意见（改用 `code-review`）；
- 需求本身模糊、尚未落到「要改哪个系统」（改用 `requirements-analysis`）。

**判断依据**：若问题是「这个项目/这块代码现在是什么样」，用本 Skill；
若问题是「应该改成什么样」或「改得对不对」，用其它 Skill。

## 适用范围

- 输入：一个可读取的项目目录（本地路径或当前工作目录）。
- 权限边界：只读。允许读取文件、列目录、查看依赖清单与配置。
- 适用：任意语言与技术栈。报告中的「未确认」是正常产物，不是缺陷。

## 与其它 Skill 配合

| 关系 | 说明 |
| --- | --- |
| 上游输入 | 不强制依赖任何其它 Skill；可直接对当前工作区执行 |
| 下游消费 | 报告可作为 `requirements-analysis`（影响面）、`architecture-design`（现状事实）、`software-development`（改动落点）的可选输入 |
| 运行时依赖 | **无**。本 Skill 可独立调用并独立完成 |
| 典型组合 | 复杂任务按「分析 → 需求 → 设计 → 实施 → 审查」组合；简单任务可跳过本 Skill |

> 组合是**可选**的典型流程，不是强制顺序；不得因为「流程还没走到」而拒绝单独调用本 Skill。

## 执行步骤

1. **检查项目目录**：列出顶层结构，识别源码、配置、文档、测试、构建与部署目录；
   记录仓库根目录判定依据（如 `.git`、`pyproject.toml`、`package.json`）。
2. **阅读项目入口文档**：按存在性依次读 `README*`、`CONTRIBUTING*`、项目级工程规范入口
   （若存在）、`docs/` 下的索引文档；提取项目目标、运行/构建/测试命令与既有约定。
   文件不存在就写「不存在」，不假设其内容；不预设任何具体 AI 工具的文件名。
3. **检查依赖和技术栈**：读取依赖清单与锁文件、运行时版本声明、构建配置、
   容器与 CI 配置；列出语言/框架/主要库及版本来源，区分「声明的」与「实际锁定的」。
4. **分析模块边界**：从入口文件与路由/注册点出发，列出主要模块、各自职责、
   公开接口、依赖方向；标记循环依赖与边界模糊处。
5. **分析数据流和调用关系**：针对 1–2 条关键用例，追踪从入口到持久化再返回的路径，
   标注校验点、写入方、外部系统、异步边界与失败行为。
6. **检查数据库结构**：定位 schema、迁移脚本、ORM 模型、数据访问层；记录主要实体、
   约束、索引、迁移方式与租户/权限相关字段。没有数据库就明确写「无」。
7. **检查测试体系**：定位测试目录与框架、测试命令、分层情况、fixture 与 CI 门禁；
   记录哪些关键路径有测试、哪些没有。
8. **识别技术债务和风险**：只记录有证据的项（文件路径 + 现象 + 影响），
   例如缺少测试的高风险模块、未锁定的依赖、过时文档、暴露的调试接口。
   不给「应该重写」这类无依据的结论。
9. **输出项目分析报告**：按 [报告模板](assets/report-template.md) 组织，
   附上「已确认事实 / 未确认事项 / 需用户澄清的问题」。

## 输入要求

| 输入 | 必需 | 缺失时 |
| --- | --- | --- |
| 项目根路径 | 是 | 使用当前工作目录，并在报告中说明 |
| 关注点 | 否 | 按默认 9 步全量分析 |
| 只读权限 | 是 | 若环境不允许读取，列出无法访问的路径并停止，不猜测其内容 |

**不假设**任何文件、接口、数据库字段或依赖存在。每一步的结论都附来源路径。

## 输出要求

产出一份 Markdown 报告，章节固定为：

1. 概览（项目目标、根目录判定依据、技术栈一览）；
2. 目录结构与关键文件；
3. 依赖与技术栈（含版本来源）；
4. 模块边界与依赖方向；
5. 关键数据流与调用关系；
6. 数据库结构（或「无」）；
7. 测试体系；
8. 技术债务与风险（证据 + 影响 + 建议，不虚构）；
9. 已确认事实 / 未确认事项 / 需用户澄清的问题；
10. 下一步建议（只读，不写入文件）。

模板见 [assets/report-template.md](assets/report-template.md)。

## 质量检查

- [ ] 每条结论都能指向具体文件路径或命令输出；
- [ ] 不存在的文件/字段被明确标为「未确认」，没有凭空补齐；
- [ ] 依赖版本区分了「声明」与「锁定」；
- [ ] 模块边界中包含依赖方向与循环依赖结论；
- [ ] 至少一条关键数据流被完整追踪（含失败行为）；
- [ ] 技术债务每条都有证据，没有「建议重写」这类无依据判断；
- [ ] 全程未发生任何写操作。

## 完成标准

- 9 个步骤全部执行（不适用的写明原因），报告 10 个章节齐全；
- 未确认事项与需澄清问题已单列，且给出**可回答的**澄清问题
  （已确认事实 + 不确定点 + 可选路径 + 各自后果）；
- 报告可直接作为 `requirements-analysis` / `architecture-design` 的输入；
- 项目代码零改动。

## 异常情况处理

| 情况 | 处理 |
| --- | --- |
| 目录不是仓库根 / 结构异常 | 说明判定依据与不确定范围，按可读到的最深层级分析，标注局限 |
| 入口文档缺失或过期 | 写「缺失/疑似过期」并给出证据，不用常识补全项目约定 |
| 依赖清单无法解析 | 记录原始内容与解析失败原因，标为未确认 |
| 无数据库 / 无测试 | 明确写「无」，并说明这可能带来的风险 |
| 文件过大或数量过多 | 记录抽样范围与抽样依据，说明哪些部分未覆盖 |
| 读取被权限或环境阻止 | 停止相关步骤，列出受阻路径与需人工补充的信息，不绕过 |
| 用户要求「顺便改一下」 | 拒绝在本 Skill 内实施，提示改用 `software-development` 并另行授权 |
