# 项目分析详细检查清单

> 由 `project-analysis` 的「执行步骤」按需加载。每一项都要求可追溯的来源路径。

## A. 目录与入口

- [ ] 顶层目录逐个列出，不与"常见项目结构"做对照推断
- [ ] `README*`、`CONTRIBUTING*`、项目级 AI 工具规则入口文件（若存在，按实际文件名记录）存在性逐一确认
- [ ] `docs/` 下的索引/架构/部署文档存在性确认
- [ ] 记录根目录判定依据（`.git`、语言清单文件、构建配置）
- [ ] 记录明显的入口文件（main / app / server / index）与其实际内容

## B. 依赖与技术栈

- [ ] 依赖清单与锁文件都读取，区分「声明」与「锁定」
- [ ] 运行时版本声明（`.python-version`、`.nvmrc`、`engines`、`Dockerfile` 基础镜像）
- [ ] 构建工具与脚本入口（Makefile / justfile / package scripts / task runner）
- [ ] CI 配置中的实际命令与门禁顺序
- [ ] 容器与部署文件（compose / K8s / 部署脚本）
- [ ] 标注来源可疑或已弃维护的依赖，但不断言"应该替换"

## C. 模块边界

- [ ] 每个主要模块写一句话职责，附入口文件路径
- [ ] 从路由/注册点反查模块关系，而不是只看目录名
- [ ] 记录公开接口与内部实现的分界
- [ ] 记录依赖方向，标出双向依赖或环
- [ ] 记录共享可变状态、全局单例、跨模块直连数据库等隐性耦合

## D. 数据流

- [ ] 选 1–2 条关键用例（优先写操作、涉及外部系统的路径）
- [ ] 标注：入口、校验点、转换、唯一写入方、事务边界、异步分界
- [ ] 标注外部系统调用的超时/重试/失败补偿（若代码中可见）
- [ ] 标注失败时数据可能处于什么状态
- [ ] 无法追踪的部分写明在哪一步断掉、为什么

## E. 数据库

- [ ] schema / 迁移目录 / ORM 模型 / 数据访问层分别定位
- [ ] 主要实体、主键、唯一约束、索引、外键或等价保证
- [ ] 迁移命名与执行顺序，是否有回滚脚本
- [ ] 租户/权限相关字段与隔离方式
- [ ] 无数据库时明确写「无」

## F. 测试

- [ ] 测试目录与命名约定
- [ ] 框架与运行命令（从配置或文档确认，不猜）
- [ ] 分层：单元 / 集成 / API / E2E 各自是否存在
- [ ] fixture / 工厂 / 测试数据库准备方式
- [ ] CI 中测试是否作为门禁
- [ ] 关键路径覆盖缺口（附证据）

## G. 技术债务与风险（只记有证据的）

- [ ] 未锁定依赖、过期文档、缺失测试的高风险模块
- [ ] 暴露的调试接口、硬编码环境值、可疑密钥（只报位置，不复制密钥内容）
- [ ] 明显的循环依赖、超大模块、重复实现
- [ ] 每条都有：路径 + 现象 + 影响 + 建议 + 置信度

## H. 反模式（本报告禁止出现）

- 凭目录名推断模块用途；
- 把"通常这类项目会…"写成事实；
- 用「未发现」代替「未检查」；
- 在报告中夹带重写建议或技术选型结论；
- 调研期间修改任何文件。
