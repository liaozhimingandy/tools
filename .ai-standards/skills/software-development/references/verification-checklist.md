# 验证与汇报清单

> 由 `software-development` 步骤 7、9、10 按需加载。
> 核心原则：结论必须来自实际执行的命令输出。

## 1. 执行前确认

- [ ] 已从项目文档/配置确认 lint、类型检查、测试、构建的真实命令
- [ ] 已确认正确的配置文件（composite 项目需显式 `-p tsconfig.app.json` 等）
- [ ] 已确认环境变量、测试数据库、依赖已就绪；未就绪的列为「未运行项」
- [ ] 未跳过钩子、未关闭检查、未使用 `--no-verify`

## 2. 四类检查分别执行

| 检查 | 目的 | 常见假阴性 |
| --- | --- | --- |
| 静态检查 | 格式、未使用导入、明显缺陷 | 只跑格式化不跑 lint |
| 类型检查 | 类型安全 | 根目录零输出的 composite 项目；`@/` 别名未配到 tsconfig 导致导入退化成 `any` |
| 测试 | 行为正确性 | 只跑与本次改动相关的用例；用覆盖率代替断言 |
| 构建 | 产物可生成 | 用构建成功代替类型检查/测试 |

**注意**：类型检查通过 ≠ 构建通过；构建通过 ≠ 测试通过。三者独立记录。

## 3. 大范围改动前后的隔离验证

1. 格式化前跑一次类型检查与构建，保存结果；
2. 格式化后各跑一次，比较错误集（`文件 | 错误码`），
   新增项才算真回归；
3. 若别名/配置被修正导致错误数先变多，说明原本被掩盖的问题显现，不是退化；
4. 临时用于对照的配置文件用完删除，不留在交付里。

## 4. 失败处理

- [ ] 失败用例名与失败原因已记录
- [ ] 定位根因并修复后重跑受影响的检查
- [ ] 未修改断言绕过失败、未删除失败用例、未跳过检查
- [ ] 无限重试或不稳定的测试先修根因，不用 `sleep` 掩盖
- [ ] 无法修复的失败如实保留在报告中，状态写「已运行但失败」

## 5. 环境受限时

- [ ] 明确写出哪些检查未运行、为什么
- [ ] 给出需人工验证清单：命令 + 预期结果 + 风险
- [ ] 报告中不得出现「测试通过」「已验证」等表述
- [ ] 不得把 lint / 构建结果冒充测试结果

## 6. 汇报前的最后核对

- [ ] 三种状态分别列出：已验证通过 / 已运行但失败 / 未运行（原因）
- [ ] 每条状态都有对应命令与真实输出摘要
- [ ] 失败或未运行项写在报告开头
- [ ] 修改内容、验证结果、风险与未决项、后续动作四项齐全
- [ ] 完成度如实填写，未夸大

---

## 禁止

- 编造命令输出、复制他人输出冒充本次运行；
- 把「应该会通过」「理论上没问题」写成「已通过」；
- 在没有执行测试的情况下宣称测试通过。
