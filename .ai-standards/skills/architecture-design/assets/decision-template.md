# 设计决策记录（ADR）模板

> 每条重要决策复制一份。目的：半年后接手者不看对话历史也能理解「为什么这样设计」。

## ADR-〈编号〉：〈决策标题〉

| 项 | 内容 |
| --- | --- |
| 日期 | 〈日期〉 |
| 状态 | 提议 / 已接受 / 已废弃 / 被 ADR-〈编号〉取代 |
| 关联需求 / 设计文档 | 〈标识〉 |
| 决策者 | 〈角色或人名〉 |

### 问题

〈一句话说明要解决什么、为什么必须现在决定。写事实，不写方案。〉

### 备选方案

| 方案 | 做法 | 优点 | 缺点 / 代价 |
| --- | --- | --- | --- |
| A | 〈做法〉 | 〈优点〉 | 〈代价〉 |
| B | 〈做法〉 | 〈优点〉 | 〈代价〉 |
| C（可选） | 〈做法〉 | 〈优点〉 | 〈代价〉 |

### 选择

〈明确写出选了哪个方案。〉

### 理由

- 〈与需求/约束直接相关的理由〉
- 〈被放弃方案的关键缺陷〉
- 〈取舍：用什么换了什么〉

### 后果

- 正面：〈影响〉
- 负面 / 债务：〈影响，以及由谁承担〉
- 需要同步更新的：〈文档 / 配置 / 测试 / 部署 / 迁移〉

### 重新评估条件

〈写明「出现什么情况时应重新评估本决策」，例如数据量级、团队规模、
上游依赖变化、官方能力变更。〉

### 待确认 / 需授权事项

〈逐条；无则写「无」。涉及新增依赖、契约变更、数据结构变更时必须显式列出。〉

---

## 填写说明

- 决策必须可推翻：没有「重新评估条件」的记录视为不完整。
- 不要把多条不相关决策塞进一份 ADR。
- 决策记录随设计文档一起版本化，不散落在聊天记录里。
- 决策被取代时新建 ADR 并把旧记录状态改为「被取代」，不要直接改写历史结论。
