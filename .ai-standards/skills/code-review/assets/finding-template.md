# 审查问题条目模板

> 每条真实问题复制一份。以下 6 个字段缺一不可（依据为推荐附加字段）。
> 问题描述必须能在 diff 中核对；推测标注「待确认」并给出确认方法。

## 〈编号〉·〈严重程度〉·〈一句话标题〉

| 字段 | 内容 |
| --- | --- |
| 严重程度 | `CRITICAL` / `HIGH` / `MEDIUM` / `LOW` / `INFO` —〈判定依据〉 |
| 文件及代码位置 | 〈路径〉:〈行号或函数/符号名〉 |
| 问题描述 | 〈客观描述 diff 中发生了什么，不写「感觉」「似乎」「不够优雅」〉 |
| 触发条件 | 〈在什么输入 / 状态 / 并发条件下会发生〉 |
| 实际影响 | 〈后果 + 涉及的接口、模块、数据或调用方〉 |
| 建议修复方案 | 〈可执行方向，例如「在 X 处增加对象级授权校验，并对列表接口逐条过滤」〉 |
| 关联维度 | 〈10 个维度之一〉（附加） |
| 依据 | 〈规范条目或验收标准编号〉（推荐附加） |
| 状态 | 已确认 / 待确认（附加） |

> 引用关键代码片段时只贴必要行。修复方案不写「建议优化一下」「可以考虑重构」。

### 待确认时补充（状态为「待确认」才填写）

- 缺少的信息：〈说明〉
- 确认方法：〈问谁 / 查哪个文件 / 跑哪条命令〉
- 若确认成立应升级为：〈严重程度〉

---

## 填写说明

- 一条问题只写一件事；不要把多个缺陷塞进同一条。
- 同一根因在多处出现时合并为一条，并在「文件位置」列出全部位置。
- 没有发现任何问题时不要复制本模板凑数：直接输出空问题清单 +
  各维度「未发现问题」结论。
