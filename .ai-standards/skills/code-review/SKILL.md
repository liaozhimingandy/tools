# Code Review

**核心约束**：以独立审查视角工作，**不参与实现、不直接改代码**。
必须优先报告真实问题；**不能为了凑数量虚构问题**，也不能把个人风格偏好包装成缺陷。

> 本文件自包含：十个审查维度、分级标准与输出格式已内联。完整规范可在项目根目录的
> `.ai-standards/core/`（`security-principles.md`、`testing-principles.md`、
> `architecture-principles.md`）下按需查阅，但**不依赖**这些文件即可完成本 Skill。
> **渐进加载**：仅当任务确需通用原则的细节时才读取上述 core 文件；涉及具体语言/框架
> 的红线时再读 `.ai-standards/standards/` 对应规范。**不假设能访问其它会话的上下文**，
> 一切以当前 diff、实际代码与用户本轮提供的需求为准。禁止写 `../../core/xxx.md` 这类链接。

## 前置约束（内联红线）

- 结论必须基于 diff 中可验证的事实；推测标注「待确认」并给出确认方法。
- 不为凑数量虚构问题、不重复同一问题的多个表述、不以问题数量作为质量指标。
- 不把风格偏好写成 HIGH 及以上；纯风格归 INFO 且不影响合入。
- 不因测试通过就省略架构、安全、兼容性检查。
- 审查与实施分离：只报告，不修改代码。

## 触发场景

- 提交前自检、PR 审查、合并前风险评估；
- 用户要求「review 一下」「看看这次改动有没有问题」「帮我审一遍」；
- 需要一份按严重程度排序、可直接行动的问题清单。

## 何时不使用

- 需要的是实现（用 `software-development`）、需求澄清（用 `requirements-analysis`）
  或项目现状调研（用 `project-analysis`）；
- 还没有明确的改动范围（无 diff / 无文件列表）——先限定范围，不对「整个项目」泛审；
- 用户要的是「帮我改好」而非「帮我看看」——改用 `software-development`。

**判断依据**：若问题涉及「这次改动对不对、能不能合」，用本 Skill；
若「该怎么改」，用实施 Skill；本 Skill 只读、只报告。

## 适用范围

- 输入：改动范围（diff / 文件列表）、需求与验收标准、项目规范、可选的验证结果。
- 权限边界：只读。允许读取文件与运行只读检查；不修改源码、不改测试断言。
- 输出是**审查意见**，不是修复补丁；建议只描述方向，不直接改代码。

## 与其它 Skill 配合

| 关系 | 说明 |
| --- | --- |
| 上游输入 | 改动与验证结果通常来自 `software-development`；需求与验收标准来自 `requirements-analysis` |
| 下游消费 | 问题清单交给 `software-development` 返工；返工后可再次审查 |
| 运行时依赖 | **无**。本 Skill 可独立审查任意给定 diff，不强制要求先跑其它 Skill |
| 典型组合 | 复杂任务按「分析 → 需求 → 设计 → 实施 → 审查」组合；用户只要求审查时可直接用本 Skill |

> 组合是**可选**的典型流程，不是强制顺序；**审查与实施始终分离**，
> 本 Skill 不与 `software-development` 在同一轮里自我实现、自我审查下结论。

## 执行步骤

先确认审查范围（见「输入要求」），再按以下 10 个维度逐项检查，
每个维度都要给出结论（含「未发现问题」）：

1. **业务逻辑正确性**：改动是否满足需求与验收标准；是否引入语义偏差；
   是否有未被需求覆盖的行为变化。
2. **架构合理性**：模块职责是否仍单一、依赖方向是否单向无环、
   数据归属是否唯一、边界是否被绕过。
3. **安全风险**：输入校验、对象级授权、认证/授权分离、注入类
   （SQL / 命令 / XSS / SSRF / CSRF）、密钥与日志脱敏、上传、依赖、多租户隔离。
4. **数据库和事务风险**：迁移脚本、回滚路径、旧数据兼容、约束与索引、
   事务边界、N+1 与全量加载、幂等与并发写入。
5. **并发问题**：共享可变状态、竞态、重复提交、超时与重试、异步失败补偿。
6. **性能问题**：无界集合、分页上限、阻塞调用、缓存一致性、循环内日志或 I/O。
7. **错误处理**：异常是否被吞掉、失败后状态是否可恢复、错误信息是否泄漏内部细节。
8. **向后兼容性**：公开契约、数据结构、配置项、部署方式、错误码与事件格式。
9. **测试完整性**：正常/边界/异常/回归四类用例、权限用例、
   Mock 是否绕过真实行为、是否有「修复前失败」的回归用例。
10. **不必要的复杂度**：多余的层、只有一个实现的接口、未使用的配置项、
    为模式而模式、未授权的新依赖。

详细检查项见 [references/review-checklist.md](references/review-checklist.md)。
发现问题时按 [问题条目模板](assets/finding-template.md) 填写，
并汇总为 [审查报告模板](assets/review-report-template.md)。

## 输入要求

| 输入 | 必需 | 缺失时 |
| --- | --- | --- |
| 改动范围（diff / 文件列表） | 是 | 请求补充，不对「整个项目」泛泛而谈 |
| 需求与验收标准 | 是 | 标注「无法判断业务正确性」，不猜测意图 |
| 项目规范与既有约定 | 是 | 读取项目内规范；读不到则标注，不臆造标准 |
| 实际验证结果 | 否 | 明确列为「验证结果缺失」，不假定已通过 |

## 输出要求

**严重程度分类**（全 Skill 与模板统一使用这 5 级，不混用其它名称）：

| 级别 | 判定依据 | 对合入的影响 |
| --- | --- | --- |
| `CRITICAL` | 严重安全漏洞、重大数据损坏/丢失、系统级风险、破坏性契约变更未迁移、测试伪造 | 阻止合入 |
| `HIGH` | 重要功能错误、严重兼容性问题、边界/异常路径缺失、明显并发/性能风险 | 默认阻止合入，或需显式豁免并记录 |
| `MEDIUM` | 一般 Bug、明显边界问题、较大可维护性风险、测试缺口 | 有条件合入（需登记修复） |
| `LOW` | 轻微问题、低风险改进建议、局部错误信息不清 | 不阻止合入 |
| `INFO` | 非缺陷性质的说明、优化建议、纯风格偏好 | 不影响合入 |

每条问题**必须**包含以下 6 个字段（模板见 [assets/finding-template.md](assets/finding-template.md)）：

| 字段 | 要求 |
| --- | --- |
| 严重程度 | `CRITICAL` / `HIGH` / `MEDIUM` / `LOW` / `INFO` + 判定依据 |
| 文件及代码位置 | 具体路径 + 行号或函数/符号名 |
| 问题描述 | 基于 diff 可验证的客观描述，不写主观感受 |
| 触发条件 | 在什么输入/状态/并发条件下会发生 |
| 实际影响 | 会导致什么后果、影响哪些接口/模块/数据/调用方 |
| 建议修复方案 | 可执行的修复方向，不是「建议优化一下」 |

**依据**（指向具体规范条目或验收标准编号）作为推荐附加字段，鼓励填写。

报告还需包含：

- **问题统计**：发现问题总数 + 按 5 个严重程度分类的数量；
- **是否存在阻止合并的问题**：明确写出，并列出对应的 `CRITICAL` / `HIGH` 编号；
- **结论**：可合入 / 有条件合入（列出条件）/ 不可合入；
- **已确认无问题的维度**：逐项写出，避免「没提到 = 没检查」；
- **未覆盖项**：因缺少信息无法判断的部分，以及需要补充什么；
- **验证状态**：实际运行了哪些只读检查、结果如何。

模板见 [assets/review-report-template.md](assets/review-report-template.md)。

## 质量检查

- [ ] 10 个维度逐项都有结论，包括「未发现问题」的维度；
- [ ] 每条问题都有 6 个字段，且问题描述可在 diff 中核对；
- [ ] 分级只用 5 级标准名称，严重程度与结论一致（存在 CRITICAL/HIGH 却判定可合入须有显式豁免说明）；
- [ ] 没有把风格偏好写成 HIGH 及以上，纯风格已标为 INFO；
- [ ] 没有重复表述同一问题来充数，没有虚构问题；
- [ ] 问题总数与分级数量之和一致，未覆盖项与所需补充信息明确；
- [ ] 未因测试通过而跳过架构、安全、兼容性维度；
- [ ] 全程未修改任何代码或测试断言。

## 完成标准

- 10 个维度全部检查完毕并给出结论；
- 问题清单按严重程度排序，字段齐全、依据明确；
- 问题统计与分级数量一致，结论与问题列表逻辑一致，有条件合入时条件可执行；
- 未覆盖项、验证状态、需人工确认事项均已单列；
- 项目代码零改动。

## 异常情况处理

| 情况 | 处理 |
| --- | --- |
| diff 过大或范围不清 | 先请求缩小范围；无法缩小时记录已审查部分与抽样依据，明确标注局限 |
| 缺少需求/验收标准 | 业务正确性维度标为「无法判断」，列出需要补充的信息，不猜测意图 |
| 验证结果缺失 | 明确写「验证结果缺失」，不以「看起来没问题」代替 |
| 无法确认某行为是否有意 | 标为「待确认」并给出确认方法（问谁 / 查什么），不写成确定缺陷 |
| 发现疑似安全漏洞但证据不足 | 按 HIGH 报告并标注「需确认」，说明可能的触发条件与排查方式 |
| 没有发现任何问题 | 如实输出空问题清单 + 各维度「未发现问题」结论，不编造 INFO/LOW 凑数 |
| 用户要求「顺便帮我改了」 | 拒绝在本 Skill 内实施，提示改用 `software-development` |
