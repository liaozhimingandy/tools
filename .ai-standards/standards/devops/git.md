# Git 与版本控制规范

> **何时读**：建分支、提交、合并、回滚、处理冲突、打标签时。
> **红线**：[../../core/ai-behavior.md](../../core/ai-behavior.md) §3.10 ——
> 推送、强推、删除远端分支等外部/不可逆动作必须获得明确授权。
> **前提**：[../../core/engineering-principles.md](../../core/engineering-principles.md) §4（最小必要修改）。

---

## 1. 先诊断，再操作

**规则**：任何合并、重置、回滚前，先确认仓库真实状态。

- 至少检查：当前分支、工作区是否干净、是否有未提交改动、与远端的领先/落后关系、
  是否存在进行中的 rebase/merge/cherry-pick、是否有未推送提交。
- 不盲目执行 `reset --hard`、`push --force`、`checkout --` 或"先拉再覆盖"，
  优先使用可恢复的替代方案。
- 存在用户未提交改动时，**不代为丢弃**，先列出并询问。

## 2. 分支

- 遵循项目既有分支模型与命名约定，不擅自引入新模型。
- 分支生命周期短；一个分支只承载一个可独立评审的变更。
- 不在共享主分支上直接做实验性提交。
- 长期分支定期同步基线，避免一次性解决巨量冲突。

## 3. 提交

- 一个提交一个逻辑变更；不顺手夹带格式化、重命名、依赖升级，除非用户明确要求。
- 提交信息说明"为什么"而不仅是"改了什么"；遵循项目既有格式（如 Conventional Commits）。
- 提交前逐文件核对 `git diff`，确认没有调试代码、密钥、临时文件、生成物误入。
- 不把失败的测试注释掉、不跳过检查来"先提交"。
- 不跳过钩子（`--no-verify`）或签名，除非用户明确要求；钩子失败时修复根因。

## 4. 合并与冲突

- 冲突按**语义**解决，不按"保留我这边"一键处理；对每个冲突块确认两侧意图。
- 合并后重新运行类型检查、测试、构建；合并本身可能引入语义冲突。
- 优先使用可追溯的合并方式；改写历史前确认没有他人基于该历史工作。
- 冲突解决后检查是否意外删除了业务功能，见
  [../../core/ai-behavior.md](../../core/ai-behavior.md) §3.4。

## 5. 回滚

- 优先使用 `git revert` 生成可逆的反向提交；改写共享历史需单独授权。
- 回滚前确认：影响哪些提交、是否涉及数据库迁移（代码回滚不等于数据回滚）、
  是否有下游依赖、是否需要同时回滚配置或迁移脚本。
- 数据库相关回滚见 [../backend/database.md](../backend/database.md)。
- 回滚后验证原问题消失且未引入新问题，并记录原因。

## 6. 标签与发布

- 标签与版本号一致且可追溯，见 [../../docs/versioning.md](../../docs/versioning.md)。
- 发布说明列出：变更内容、破坏性变更、迁移步骤、验证结果。
- 不擅自创建/移动已发布的标签；标签移动属破坏性操作。

## 7. 仓库卫生

- `.gitignore` 覆盖：构建产物、本地配置、密钥文件、IDE 文件、日志、虚拟环境。
- 大二进制文件、生成物不入库；确需入库时说明原因与管理方式。
- 不提交真实凭据；一旦泄漏必须**轮换**，仅从最新提交删除不等于修复，见
  [../../core/security-principles.md](../../core/security-principles.md) §8。
- 换行符与编码遵循仓库既有配置；批量格式化前先统计 CRLF/LF 与缩进分布，
  避免产生整文件级别的无意义 diff。

## 8. 提交前自检

1. 工作区状态已诊断，用户改动未被覆盖。
2. `git diff --stat` 中每个文件都能追溯到本次需求。
3. 无密钥、无调试代码、无无关格式化 diff。
4. 类型检查 / 测试 / 构建已实际运行并记录结果。
5. 未执行的外部动作（push/强推/删除远端）已明确标注为待用户操作。
